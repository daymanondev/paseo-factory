# 0060 — Rotate Seats: The One Explicit No-Handover Replacement

- **Date:** 2026-11-14
- **Status:** Accepted. The Owner approved the spec; implemented on `spec/factory-rotate-seats`, shipped in v0.10.0.
- **Amends:** [ADR 0057](0057-every-seat-replacement-is-a-handoff-supervisor-handoff-and-wide-colourful-factory-tab.md) Decision 1. The rule "every seat replacement is a handoff" and the removal of "every retire-seat path that archives without a handover" gain one explicit, Owner-only exception.
- **Spec:** `.scratch/factory-rotate-seats/spec.md`.

## Context

ADR 0057 Decision 1 removed the old Rotate button because the Owner then replaced seats only when they were failing mid-work, and a handover is what that case needs. The long-idle Project is a different case. The Owner comes back after a long break and wants the old Supervisor and Lead gone and the next seats to start clean. Every way to replace them today passes the old context forward:

- **Hand off now** extracts a handover from the outgoing seat.
- **Replace now** skips extraction, but the successor still gets a plugin-built Substitute handover.
- **Archiving the Lead from outside** triggers lost-Lead recovery, which recreates the Lead with a Substitute handover.
- **Project reset** drops the seats, but it also wipes the Ledger, the notebook and the worktrees and resets the repository. That is far too destructive for "start the seats over".

## Decision

1. **Rotate seats is a new Owner-only Project act.** One action retires a Project's Supervisor and Lead together, with no extraction and no Substitute handover. It is the single exception to ADR 0057 Decision 1. Rotating one seat alone is not offered.
2. **It refuses while a live Peer exists.** The server refuses with `peers-live` when any live, non-`error` Peer is bound to a Task of the Project that is not accepted or closed. The module is the one that holds the Lead's quiet point (v0.8.5, ADR 0058), shared in `plugin/server/peer-in-flight.ts`, and it computes its own inputs (the Project's Ledger stream and queued mail) for both callers. The two callers differ in one law: the quiet point treats a Peer-terminal outcome or a queued Peer challenge or blocker as handing the Task back to the Lead, but Rotate does not. A queued Peer challenge is exactly the work Rotate would delete, so queued mail never settles a Task for Rotate. An idle or paused Peer counts. Rotate also refuses with `handoff-in-progress` while a Peer handoff is running, and with `ledger-unreadable` when the Project's Ledger cannot be read, because an unreadable Ledger cannot prove there is no live Peer. Every refusal names what holds and changes nothing: no seat archived, no file deleted. Open Tasks with no live Peer are fine and stay in the Ledger. Rotate never cancels, resets or archives a Peer, and never touches a Peer's handoff state.
3. **Retire order is mail, Lead, Supervisor, records.**
   1. Call the Lead-mailbox runtime's `rotateProjectMailbox` first. It moves the Project's seat epoch, clears the Project's seat runtime (handoff timers and progress, kickoff flags, the persisted rotation fields) and drops the on-disk records, each through the module that owns it: `mailbox.jsonl`, `lead-handoff.md` and `lead-handoff-extraction.json` by the mailbox runtime, the Supervisor's records by its handoff runtime. The Peers' handoff state is not part of it.
   2. Retire the **Lead first, then the Supervisor**, through the existing marked-archive path (`retireSeat`). Every archive is marked as the plugin's own (ADR 0057 Decision 4), so lost-Lead recovery never fires. Lead first means a pre-v0.6.1 Supervisor with a still-parented Lead is archived, not merely "released". A released Supervisor waiting on the Lead is archived with it.
   3. Clear the registration's seat and handoff fields, retire both seats once more by label (a sweep for any seat that appeared in the meantime), then call `rotateProjectMailbox` again, because the Lead's retire requeues its un-acked batch into the mailbox file.
   4. A Project with no bound seat succeeds and says nothing was archived.
   5. If a seat retire fails after the records were dropped, the reply says so plainly: Rotate stopped partway, the mail and handover records were already dropped, which seats were archived, which seat is still bound, and to run Rotate again. The act is safe to re-run: the peer check passes again, the clear is idempotent, and a seat that is already gone retires as nothing.
4. **What is dropped and what is kept.**
   - Dropped: `mailbox.jsonl` (held and un-acknowledged mail), `lead-handoff.md`, `lead-handoff-extraction.json`, `supervisor-handoff.md`, `supervisor-handoff-extraction.json`, both handoff progress records, and the registration's `supervisor`, `lead`, `releasedSupervisors`, `rotationState` and `handoffRequestedAt`. An in-flight handoff (scheduled, handing over, creating successor) is cancelled with them, and a half-created successor is archived as a live seat candidate.
   - Kept: the Project notebook, `lanes.json`, the Ledger and its open Tasks, `usage.json` (the retire flushes the seats' final usage first), Task worktrees and workspaces, and the registration itself (`root`, `workspaceId`, `paseoProjectId`, `taskWorkspaces`, `dispatchers`). Rotate never calls the Project cleanup that archives Peers and deletes worktrees.
5. **Nothing restarts by itself.** Afterwards the Project has no Supervisor and no Lead (ADR 0057 Decision 5 is unchanged). The Owner opens a New Chat with the `Supervisor (Factory)` profile at the Project root, which binds fresh. That Supervisor's first dispatch creates a fresh Lead whose Turn-1 packet carries the standard kickoff (repository facts, Ledger task summary, notebook) and no handover and no staleness notice. The reply names this next step.
6. **Contract and lane.** The act is the RPC `factory.project.rotate` (`input: { projectRoot?, project? }`; ok output `{ project, projectRoot, archivedSeats, summary, view? }`). Failure codes: `unknown-project`, `ambiguous-project`, `seat-cannot-rotate`, `daemon-unavailable`, `ledger-unreadable`, `peers-live`, `handoff-in-progress`, `project-rotate-unavailable` (the daemon's plugin has no handler, or no Lead-mailbox runtime is wired), and the seat retire failures (`archive-failed` and kin, worded as in Decision 3.5). It resolves the Project with the same block as Project reset, now extracted as one helper. It runs under the target Project's exclusive-maintenance lane, so it cannot interleave with reset, delete or register of that Project. The Spool kind is `project_rotate`, matching `project_register` and `project_delete` and never confusable with the legacy `lead_rotate` and `rotation_*` Lead handoff; the CLI verb stays `factory project rotate`. The CLI verb and menu item only wrap the handler. A stamped seat is refused (`seat-cannot-rotate`) both at the Spool and by the handler itself.
7. **A handoff in flight cannot survive the act (the seat epoch).** The Lead-mailbox runtime keeps a per-Project seat epoch. `rotateProjectMailbox` (and a Project reset) moves it, and every mailbox lane job carries the epoch it was admitted under. Rotate's lane is the target Project's own Factory, while the mailbox lane runs on the root Factory, so nothing else orders the two and a handoff paused on an await can resume after the act. Each such job therefore re-checks the epoch after every await and before every write or call that could carry old context forward: the handover file or Substitute, the extraction record, the Lead retire, the successor create, the kickoff delivery, the rotation-state writes. A job whose epoch moved abandons itself, and a Lead it had just raised is retired. Together with the per-seat serialization of seat create and retire (an in-flight create is retired by Rotate's retire, never missed) and Rotate's final sweep, no path leaves a live Lead, a `lead-handoff.md` or a Substitute behind.

## Consequences

- The Owner has a non-destructive "start the seats over" for a returning Project. The only other path that drops seats without a handover is Project reset, which also wipes history.
- ADR 0057's "no retire-seat path without a handover" now reads "none except Rotate seats". Hand off now and Replace now are unchanged and remain the right tools for a failing seat mid-work.
- Open Tasks that had a Peer are refused, not closed. The Owner must let the Peer finish or close the Task first. A future ticket could offer to close them as part of the act.
- The race with a handoff or pump already running before the act began is closed, not narrowed: see Decision 7.
- The Peer-in-flight predicate now has two callers (the Lead-mailbox quiet point and the Rotate refusal) and one definition.
