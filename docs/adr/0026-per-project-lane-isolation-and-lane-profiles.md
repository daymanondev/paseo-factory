# ADR 0026 — Per-Project Multi-Provider Lane Isolation, Live-Seat Transition Warning, and Owner-Authored `Lane profile`s

- **Status:** Accepted — 2026-10-24; amended 2026-10-25 (`grill-with-docs` Q1–Q4; ratified by Andrew)
- **Amends:** [ADR 0009](0009-factory-surface-and-lane-config.md) §2–§3 (`Lane config` and `Seats & Models`), [ADR 0010](0010-project-scoped-slp-worktrees-and-lead-agent.md) §2/§5 (per-Project `lanes.json` scope), [ADR 0014](0014-private-vault-hydration-and-release-lab-companion.md) §3 (`Private vault` config sync), and [ADR 0017](0017-native-paseo-role-providers-and-slp-seat-recognition.md) §1–§2 (`Role provider` reconciliation and `agent.create` recognition)

## Context

When running multiple Projects concurrently where each Project assigns different providers and models to its six roles (`supervisor`, `lead`, `worker`, `watch`, `retro`, `freshEyes`), six cross-project and cross-provider defects surfaced in `v0.0.37` (plus four Paseo `0.13.0` New Chat picker synchronization defects resolved in the 2026-10-25 amendment):

1. **Active-Scope New Chat Picker Sync vs. Per-Project Launch Isolation (`plugin/server/surface-rpc.ts`, `src/role-providers.ts`):** Paseo Desktop's New Chat composer reads a single daemon-global `daemon.agentProfiles` / `agents.providers` from `<paseoHome>/config.json`. When the Owner updated `supervisor` or applied a `Lane profile` for the active Project, skipping `<paseoHome>/config.json` reconciliation left the `Supervisor (Factory)` New Chat picker showing stale machine-default models; conversely, relying on `<paseoHome>/config.json` alone at agent launch time would break per-Project isolation unless `server.before("agent.create")` enforces `<projectStateDir>/lanes.json` for `<config.cwd>`. Furthermore, writing `additionalModels` instead of replacement `models` on `factory-*` kept the base provider's full model catalog in `factory-supervisor`, allowing Paseo Desktop's `@paseo:create-agent-preferences` cache in `AsyncStorage` to override `agentProfiles[0].model`, and setting `extends: "antigravity"` failed `@getpaseo/protocol`'s `ProviderOverridesSchema` (`validExtendsValues = ["claude", "codex", "copilot", "opencode", "pi", "omp", "acp"]`), causing `DaemonConfigStore.reload()` to reject `<paseoHome>/config.json`.
2. **Spool Peer Spawn Provider Collision (`plugin/server/spool.ts:892-930`):** `resolvePeerSpawnProvider` rewrote a Project's default `worker` lane from `<provider>/<model>` to `factory-peer/<model>`, routing Project B's Peer onto whichever provider Project A last wrote into `factory-peer.extends` in `<paseoHome>/config.json`.
3. **Unscoped `Fresh-eyes review`, `Watch`, `Retro`, and CLI `factory run` (`src/fresh-eyes.ts`, `src/watch.ts`, `src/retro.ts`, `plugin/bin/lanes-config.mjs`):** `resolveEyeLane`, `isEyeLaneUsable`, `watchLaneAvailable`, `runWatchPass`, `retroLaneAvailable`, `runRetroPass`, and `resolveRunProvider` read `loadLanes(stateDir)` without `projectSlug`, ignoring per-Project `<projectStateDir>/lanes.json` overrides at execution time.
4. **Silent Cross-Provider Live Seat Mismatch (`plugin/server/surface-rpc.ts:1469-1509`):** When changing `supervisor` or `lead` on a Project (or at `All projects` scope) with a live seat, `lanesSet` ran `paseo agent model set <id> --model <model>` without checking whether the seat's provider family changed, leaving an existing harness session (e.g. `opencode`) running with an incompatible provider's model ID (`OpenCode model must be provider/model`) and stale Layer-1 fence, and without warning the Owner before mutating active seats.
5. **Dual-RPC Save Race on `Watch & Retro` (`plugin/client/factory/seats.tsx:656-659`):** Saving the `Watch & Retro` card fired two unawaited `lanes.set` RPCs concurrently.
6. **No Reusable `Lane profile` Mechanism:** Applying a 6-lane multi-provider setup to a Project required configuring five cards one by one, and `Private vault` did not synchronize `profiles.json` or per-app `lanes.json`.

## Decision

1. **Active-Scope `Role provider` Picker Sync with Strict Per-Project Launch Isolation.**
   - Whenever the Owner mutates `Lane config` or applies/resets a `Lane profile` (`lanesSet`, `lanesSetBatch`, `profilesApply`, `lanesReset` — whether scoped to a Project or at `All projects`), `<paseoHome>/config.json` (`factory-supervisor`, `factory-lead`, `factory-peer`, and `Supervisor (Factory)` in `daemon.agentProfiles`) is immediately reconciled from the saved scope's effective `Lanes` (and at plugin boot via `effectiveLanesForReconcile(stateDir)` using the most recently modified `lanes.json` scope) so Paseo Desktop's New Chat picker always displays the model and thinking level just configured in `Factory`.
   - Each `factory-*` entry in `agents.providers` writes replacement `models: [{ id: parsed.model, label: parsed.model, isDefault: true, ...(parsed.thinking ? { thinkingOptions: [{ id: parsed.thinking, label: parsed.thinking, isDefault: true }] } : {}) }]` (instead of `additionalModels`) so `factory-supervisor` exposes only the configured model and Paseo Desktop's `@paseo:create-agent-preferences` cache cannot stay stuck on an old model from the base provider's catalog.
   - When a lane uses a plugin-registered provider not in Paseo's built-in `validExtendsValues` (`["claude", "codex", "copilot", "opencode", "pi", "omp", "acp"]`, such as `antigravity` or `agy` without a custom `acp` `command` in `config.json`), `reconcilePaseoConfigObject` maps `factory-*.extends` to a valid built-in provider (`"pi"`, or the first non-disabled built-in provider) with replacement `models: [...]` so `<paseoHome>/config.json` always passes `@getpaseo/protocol`'s `ProviderOverridesSchema` validation and reloads cleanly. In addition, `healFactoryRoleProvidersInConfig(paseoHome)` runs before every daemon WebSocket connection (`daemonWsRequestPayload`) and CLI bridge call (`bridgeCall`, `pluginCliJson`) so any legacy/stale `factory-*` provider entry with an invalid `extends` (such as `"extends": "antigravity"` left by `v0.0.40`) is healed on disk before Paseo `0.13.0`'s `new Session()` (`loadPersistedConfig`) validates `<paseoHome>/config.json` during the WebSocket `hello` handshake.
   - In `server.before("agent.create")` (`normalizeAgentCreateRequest` in `plugin/server/choke.ts`), when a session is created with `config.provider` naming `factory-supervisor` or `factory-lead` at a Project root (`config.cwd`), the hook resolves `loadLanes(stateDir, project.slug)[seat]` and rewrites both `config.provider` (to the runtime Paseo provider ID alone: `"claude-code"` → `"claude"`, `"agy"` → `"antigravity"` unless a custom `"agy"` provider exists, or `parsed.provider` verbatim) and `config.model` (`parsed.model`, plus `thinkingOptionId`) while attaching `labels: { seat, project: project.slug }`. Because `@getpaseo/server`'s `AgentManager.createAgentInternal` passes `{ provider, model }` already split into `before("agent.create")` and immediately looks up `this.requireEnabledProvider(storedConfig.provider)`, rewriting `{ provider, model }` separately ensures every Project launches on its own configured provider and model (including `"antigravity"`) regardless of which Project last updated the New Chat picker.
   - `resolvePeerSpawnProvider` (`plugin/server/spool.ts`) returns the Project's resolved `${parsed.provider}/${parsed.model}${suffix}` directly rather than rewriting the provider prefix to global `factory-peer/...`.
   - `resolveEyeLane`, `isEyeLaneUsable`, `runFreshEyesPass`, `watchLaneAvailable`, `runWatchPass`, `retroLaneAvailable`, `runRetroPass`, and `resolveRunProvider` thread `projectSlug` (resolved from `contract.workspace` or the active Project) so per-Project `freshEyes`, `watch`, `retro`, and `worker` lanes are honored everywhere.
   - `provisionPiAgentHome` (`src/pi-home.ts`) checks existing symlink targets before replacing them so concurrent Pi session opens across Projects never race on `<stateDir>/pi-agent/<role>`.

2. **Owner-Authored `Lane profile`s (`<stateDir>/profiles.json`) with Copy-on-Apply Semantics.**
   - A **`Lane profile`** is an Owner-authored, named 6-lane map (`supervisor`, `lead`, `worker`, `watch`, `retro`, `freshEyes`) persisted in `<stateDir>/profiles.json` with an `updatedAt` timestamp (and optional tombstone records for deleted profile IDs). No built-in presets are pre-populated; the Owner creates profiles on demand from the current 6-lane configuration (`+ Save as Profile…` in `Seats & Models` or `factory profile save <id>`).
   - Applying a `Lane profile` uses **Copy-on-Apply**: it atomically writes all 6 lane values into `<projectStateDir>/lanes.json` (when a Project is selected) or `<stateDir>/lanes.json` (when `All projects` is selected) in a single batch operation (`lanes.set.batch` / `profiles.apply` — the batch RPC ships as `factory.lanes.set.batch` because RPC method names must match `/^[a-z][a-z0-9._-]*$/`, the `factory.task.detail` precedent), recording `activeProfile` metadata without creating a fragile live pointer. Tweaking a single lane afterward affects only that scope (`Modified from <Profile>`, with `Update "<Profile>"` or `+ Save as New Profile…`).
   - When a Project has a `<projectStateDir>/lanes.json` override (`hasProjectLaneOverride: true`), `Seats & Models` and `factory lanes reset --project <dir>` expose **`Reset to Machine Default`** to remove the Project's override file and inherit `<stateDir>/lanes.json`.

3. **Live-Seat Impact Warning Modal & Provider-Family Transition Law.**
   - Whenever the Owner saves a lane, applies a `Lane profile`, or clicks `Reset to Machine Default` on a Project (or at `All projects` scope when live seats inherit the machine table) that has a live `Supervisor` (`view.supervisor !== null`) and/or a live `Lead` (`view.lead !== null`), and the change mutates `lanes.supervisor` or `lanes.lead`, `Seats & Models` presents a confirmation modal (`Confirm & Apply` / `Cancel`) before executing the RPC, and the server enforces the same transition law for both Project-scoped and `All projects` saves:
     - **Same provider family** (e.g. `claude/claude-sonnet-4-6` → `claude/claude-opus-4-6:high`): the live seat's model/thinking is updated in-place via `setAgentModelViaCli`, preserving the conversation session.
     - **Different provider family** (e.g. `opencode/glm-5.1` → `claude/claude-opus-4-6:high` or `antigravity/gemini-3.1-pro-high`): the live seat's provider harness is changing, so the runtime **retires/rotates** the existing seat session (`rotateLead` for `Lead`, preserving all queued `Lead mailbox` items; cancel + archive + unbind for `Supervisor`) instead of calling `setAgentModel` across incompatible provider families, so the next turn/dispatch spawns a fresh seat on the new provider harness with the matching Layer-1 fence.
   - Changes that only touch `worker`, `watch`, `retro`, or `freshEyes` (or when no affected seat is live) apply immediately without a confirmation modal.

4. **`Private vault` Synchronization (`config/profiles.json` & Per-App `lanes.json`).**
   - `collectLocalStateIntoRuntime` and `applyVaultHydration` (`src/vault-materialization.ts`) synchronize `<stateDir>/profiles.json` ↔ `config/profiles.json` using a key-level merge by `profileId` where the newer `updatedAt` timestamp wins (preserving profiles authored on different machines), and synchronize per-Project `<projectStateDir>/lanes.json` ↔ `config/apps/<canonicalAppKey>/lanes.json` alongside store manifests.
