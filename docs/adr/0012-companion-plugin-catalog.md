# ADR 0012 — Remote-first `Companion plugin` catalog, Core + Companions `Plugins` view, on-demand update checking, and lifecycle on the `Factory surface`

- **Status:** Accepted — 2026-10-17; amended 2026-10-20 for `v0.0.25` after live UX review; amended 2026-10-22 for `v0.0.30` private/invite-only `factory-release-lab` access control; amended 2026-10-23 for `v0.0.34` two-phase `preview` → `apply` update protocol, Core self-update restart tracking, per-card elapsed progress, and persistent inline status/error banners (ratified by Andrew over `/grill-with-docs`; words "toàn bộ theo khuyến nghị của bạn")
- **Grounded in:** `@getpaseo/protocol@0.11.4` (`messages.d.ts:1468-1683,52437-52586`, `plugin.{list,source.status,source.update.preview,source.update.apply,source.install,directory.install,enable,disable,reload,remove}.request`) · `@getpaseo/client@0.11.4` (`daemon-client.js:3626-3803`, `previewPluginUpdates` / `applyPluginUpdates`) · `@getpaseo/server@0.11.4` (`plugins/index.js:274-314,573-640`, `plugins/runtime.js:228-233,408-420`) · `plugin/server/daemon-cli.ts` (`daemonWsRequestPayload`, `manageDaemonPlugin`) · `plugin/client/factory/plugins.tsx` · `plugin/client/factory/shell.tsx` · `daymanondev/factory-burn-lab` (`package.json`) · `daymanondev/factory-connector` (`package.json`) · `daymanondev/factory-release-lab` (`package.json`)
- **Amends:** ADR 0009 §2 (expands the `Factory surface` `TabBar` from three views to four views by adding `Plugins` for Core + `Companion plugin` version visibility, on-demand update checking, and lifecycle control)

## Context

`paseo-factory` is the verification core of a broader factory plugin family that includes three independent first-party Paseo plugins (ADR 0014):
- **`factory-burn-lab`** — autonomous OpenCode free-model burner (`Scout Pool`, `OSS Lab`, `Proto Arena`, `Night Shift`, `Self-Evolve`) supervised by each Project's `Supervisor` seat.
- **`factory-connector`** — symmetric peer Fleet over Tailscale (`Fleet surface`, 1-click Handoff, cooperative Burst, Fleet pulse, and Git-native Mirror repo / Fleet ref sync).
- **`factory-release-lab`** — sequential 7-phase iOS & Android store-ops and release workflow engine.

Keeping `factory-burn-lab`, `factory-connector`, and `factory-release-lab` in separate repositories and separate Paseo plugins preserves clean fault and bundle boundaries, but forces any user who installs `paseo-factory` (on macOS or Windows) to manually discover and run `paseo plugin install ...` commands for the companion plugins. Conversely, hardcoding or probing host-local sibling paths (`../factory-burn-lab`, `../factory-connector`) would couple the product to the author's local filesystem layout and fail for real users.

Paseo's daemon WebSocket session protocol already exposes first-class, cross-platform plugin management and update-status messages (`plugin.list.request`, `plugin.source.status.request`, `plugin.source.update.preview.request`, `plugin.source.install.request`, `plugin.source.update.request`, `plugin.directory.install.request`, `plugin.enable.request`, `plugin.disable.request`, `plugin.reload.request`, `plugin.remove.request`), which `paseo-factory` can invoke directly over its existing local daemon WebSocket bridge (`<home>/paseo.pid` + `<home>/local-credential`) with zero POSIX shell assumptions.

### Live UX Findings from v0.0.24 Trial (2026-10-20 Amendment)

Auditing the `Plugins` tab on Paseo Desktop exposed four concrete UX problems:
1. **Visual Clutter on Card Faces:** Each companion card stacked 6 separate blocks (`Title + id + status`, `tagline`, `description`, `capabilities` chips, an always-visible bordered `INSTALL` box with raw Git URLs, and 4 always-visible action buttons `Disable` · `Update` · `Reload` · `Remove`), creating heavy visual noise across 3–4 plugins.
2. **Missing Semantic Version (`vX.Y.Z`) & Zero Update Visibility:** Although `plugin.list.request` returns each plugin's `path` (where `<path>/package.json` or `<path>/../package.json` declares `"version"`) and `currentRevision`, the UI never surfaced `vX.Y.Z` (`v0.0.25`, `v0.0.5`, `v0.0.3`, `v0.0.2`) and never queried `plugin.source.status.request` (`updateAvailable`, `latestCommit`, `commitsBehind`). The `Owner` had no way to tell which version was installed or whether a newer version existed on GitHub.
3. **Always-Lit `Update` Button & Misleading Toast:** Every `git`/`npm`-installed plugin rendered an active `Update` button even when `commitsBehind === 0` (`updateAvailable === false`), and `pluginsManageSummary` unconditionally toasted `"updated <id> to the latest revision"` even when `plugin.source.update.response` returned `updated: false`.
4. **Core Plugin (`paseo-factory`) Invisible in `Plugins` Tab:** `paseo-factory` itself was omitted from the `Plugins` tab, leaving the `Owner` no single place to inspect the Core version/revision or check/update/reload `paseo-factory` alongside its 3 companions.

### Live Protocol & UX Findings from v0.0.33 Trial (2026-10-23 Amendment)

Clicking **`Update`** on the Core plugin (`paseo-factory`) in Paseo Desktop (`@getpaseo/server@0.11.4`) exposed three concrete failures:
1. **Retired `plugin.source.update.request` Rejected in 1ms:** `manageDaemonPlugin` (`plugin/server/daemon-cli.ts`) dispatched `{ type: "plugin.source.update.request", pluginId }`. In `@getpaseo/server@0.11.4`, `PluginService.updateSources` is retired and unconditionally throws `Error: Update the client to review plugin updates before applying them.` Instead, `@getpaseo/server@0.11.4` and `@getpaseo/cli` require the two-phase reviewed update sequence: `plugin.source.update.preview.request` (yielding `proposal` with `outcome === "update"`, `current.currentRevision`, and `target.commit`) followed by `plugin.source.update.apply.request` (`{ proposals: [proposal] }`, yielding `{ id, outcome: "updated" | "error", plugin, error, warning }`). In addition, `extractUpdateRow` parsed only the legacy `{ updated: boolean }` shape rather than the `outcome` enum emitted by `plugin.source.update.apply.response` and `paseo plugin update --yes --json`.
2. **Core Self-Update (`paseo-factory`) Stops the Calling Plugin Worker Mid-RPC:** When `PluginService.applyUpdates` updates `paseo-factory` itself, `PluginService.updateSource` runs inside the daemon process and calls `stopPlugin("paseo-factory")` before `startExplicit("paseo-factory", candidate.directory)`. `PluginRuntime.stopPluginById` immediately rejects any in-flight `plugin.rpc.invoke.request` (`factory.plugins.manage`) with `"Plugin stopped: paseo-factory"` while the daemon finishes swapping and starting the updated `paseo-factory` instance.
3. **Zero In-Flight Progress & No Persistent Inline Outcome/Error Banner in `PluginsPane`:** Unlike `VaultSyncBar` (`vaultNote` + `"Syncing Vault…"` button label), `SeatsPane` (`laneNote`), and `TimelinePane` (`retroNote`), `PluginsPane` only passed a boolean `busy` flag and relied solely on ephemeral toasts. When `plugin.source.update.request` failed in 1ms (or while a real Git clone/build ran for several seconds), button labels never changed (`"Updating… (4s)"`), cards showed no in-flight progress pill, and no persistent inline banner or per-card error box recorded the outcome or error reason.

## Decision

1. **Fourth `Plugins` view on the `Factory surface` (`TabBar`) with Compact Toolbar, Elapsed Progress Pill, and Persistent Inline Banner.**
   - `FactoryShell` (`plugin/client/factory/shell.tsx`) and `TabBar` (`plugin/client/kit/pill.tsx`) provide the fourth tab **`Plugins`** (`id: "plugins"`, icon `"Blocks"`), displaying a badge count of currently running `Companion plugin`s (`0..3`) and accessible from the global screen, workspace panel, and settings screen.
   - The `Plugins` tab opens with a compact 1-line toolbar showing ecosystem status (`Core + 3 Companions · N active on this daemon`), live action or update-check status (`Updating <id>… · Ns`, `Installing <id>… · Ns`, `Checking updates…`, `Up to date`, or `N update(s) available`), **`Check for updates`**, conditional **`Update All (N)`** (shown only when $\ge 1$ installed plugin has `updateAvailable === true`, displaying `"Updating All… (Ns)"` while active), and conditional **`Install All`** (shown only when at least one `access === "public"` companion is `not_installed`, displaying `"Installing All… (Ns)"` while active).
   - Immediately below the toolbar row, `PluginsPane` renders a dismissible **Persistent Inline Status/Error Banner** (`pluginsNote` with `statusSuccess` / `statusWarning` / `statusDanger` tone) summarizing the latest completed plugin operation (e.g. `Updated paseo-factory (0285a1c → 9f3b2c1) · v0.0.34 is now running`, `paseo-factory is already up to date (9f3b2c1)`, or the full daemon/Git error message on failure).

2. **100% Remote-first, cross-platform (`macOS` & `Windows`) catalog: Core (`paseo-factory`) + 3 `Companion plugin`s with explicit `access: "public" | "private"` tiers.**
   - `paseo-factory` ships `CORE_PLUGIN_ENTRY` (`paseo-factory` → `git:daymanondev/paseo-factory:plugin`, `access: "public"`) plus the built-in `COMPANION_CATALOG` of three official `Companion plugin`s anchored to their canonical GitHub sources and access tiers:
     - `factory-burn-lab` → `git:daymanondev/factory-burn-lab:plugin` (`access: "public"`)
     - `factory-connector` → `git:daymanondev/factory-connector:plugin` (`access: "public"`)
     - `factory-release-lab` → `git:daymanondev/factory-release-lab:plugin` (`access: "private"`, invite-only repository)
   - `FactoryView` carries `corePlugin` (`paseo-factory`) alongside `companions` (`factory-burn-lab`, `factory-connector`, `factory-release-lab`) and `pluginsCheckedAt`.
   - Clicking **`Install All`** (`target: "all"`) installs only uninstalled `access === "public"` companions (`factory-burn-lab`, `factory-connector`) and deliberately skips `access === "private"` companions (`factory-release-lab`), so public users never hit a private-repo clone failure during batch setup and the **`Install All`** button hides once all public companions are installed.
   - Clicking **`Install`** explicitly on a `private` companion (`target: "factory-release-lab"` with its canonical GitHub source) runs a pre-flight pull-access check before invoking the daemon: if `gh` is logged in, it runs `gh auth setup-git --hostname github.com` so the host's Git credential helper is wired, then probes `git ls-remote --heads <remote>` (`GIT_TERMINAL_PROMPT=0`). If the probe succeeds (e.g. Owner `daymanondev` or an invited collaborator), it dispatches `plugin.source.install.request` as usual; if it fails, it refuses with an actionable message (`private-companion-access-denied`) telling the user either to run `gh auth login` or to ask `daymanondev` to invite `@<ghUser>` as a collaborator on `daymanondev/factory-release-lab`.
   - The server **never** probes or prioritizes `../` sibling directories on the host disk.
   - On the Core (`paseo-factory`) card (`CORE` badge), `Update` (when installed from `git`/`npm`) and `Reload` are enabled, while **`Disable` and `Remove` are forbidden** (`core-plugin-protected` on `factory.plugins.manage` and omitted in the UI) so the `Owner` cannot accidentally disable or remove the active `Factory surface`.

3. **Compact 2-Row Card Layout with Version/Update/Access Pills, Per-Card In-Flight Progress & Inline Errors, Conditional Primary `Update` CTA, and Collapsible `⋯` (`Manage`) Drawer.**
   - Every plugin card (`Core` and `Companion`) renders a scannable 2-row face:
     - **Row 1 (Header):** Sidebar icon + Title + `CORE` badge (for `paseo-factory`) + `Private · Invite-only` pill (for `access === "private"` companions) + Version & Revision pill (`v0.0.5 · 7f8a5cc` for remote installs, `v0.0.25 · local` for directory installs) + Status pill (`Running`, `Disabled`, `Failed`, `Not Installed`) + `Active in Sidebar · <sidebarLabel>` pill (when `running`) + Update/In-flight status pill (`Updating 7f8a5cc → a91c3f2… · Ns` / `Installing from GitHub… · Ns` / `Reloading plugin… · Ns` in `accent` while an action targets that plugin; otherwise `Up to date`, `Update available · 7f8a5cc → a91c3f2`, or `Local`) + right-aligned Primary CTA + `⋯` (`Manage` / `Custom source…`) toggle button.
     - **Row 2 (Subtitle):** Concise 1-line `tagline` (plus daemon error or last per-card action error banner in `statusDanger` if `error !== null` or the latest action on that plugin failed, cleared when a new action starts on that plugin).
   - **Conditional Primary CTA & In-Flight Button Copy Law:**
     - When `status === "not_installed"`: primary solid CTA is **`Install`** (changing to **`Installing… (Ns)`** while in flight on that plugin).
     - When installed and `updateAvailable === true` (or while an update is in flight on that plugin): primary solid CTA is **`Update`** (changing to **`Updating… (Ns)`** while in flight).
     - When installed and `updateAvailable !== true` (and no update is in flight): **no primary `Update` button** is shown on the main card header — eliminating the always-lit `Update` anti-pattern.
   - **Collapsible `⋯` (`Manage` / `Custom source…`) Drawer:**
     - For installed plugins: reveals the 1-line install source metadata (`installKind · installedSource · shortRevision`), `capabilities` pills, and secondary lifecycle buttons (`Disable` / `Enable`, `Reload`, muted manual `Update` for remote installs, and `Remove` in `statusDanger` for companions), each reflecting its active verb (`"Disabling…"`, `"Enabling…"`, `"Reloading…"`, `"Updating… (Ns)"`, `"Removing…"`) when targeted.
     - For uninstalled companions (`not_installed`): reveals `canonicalSource`, `capabilities` pills, and the custom `Source` / `Ref (branch/tag/commit)` inputs + `Install Custom` button.

4. **Two-Phase Reviewed Update Protocol (`preview` → `apply`), Core Self-Update Restart Tracking, and On-Demand Update Check (`factory.plugins.check.updates`).**
   - Normal 5s `factory.snapshot` polls **never** run network `git ls-remote` calls; they read the 15s-cached local `plugin.list.request` (enriched with `version` from `<plugin.path>/package.json` or `<plugin.path>/../package.json`) and join any cached update status for `home`.
   - `factory.plugins.check.updates` (`pluginsCheckUpdates`) invokes `checkDaemonPluginUpdates(home)` over the daemon WebSocket (`plugin.source.status.request`, falling back to per-plugin `plugin.source.status.request` with `{ pluginId }` if the batch call fails due to an inaccessible private repository, and then to CLI `paseo --home <home> plugin update --all --check --json`), caches per-`home` update rows (`updateAvailable`, `latestRevision`, `commitsBehind`, `checkedAt`), and invalidates on any plugin install or manage call.
   - `FactoryShell` automatically triggers `pluginsCheckUpdates` once when the `Owner` opens `tab === "plugins"` (when `pluginsCheckedAt === null` or older than 5 minutes) and whenever the `Owner` clicks **`Check for updates`**.
   - `manageDaemonPlugin(home, pluginId, "update")` speaks Paseo `@getpaseo/server@0.11.4`'s two-phase reviewed update protocol over the daemon WebSocket:
     1. Dispatches `plugin.source.update.preview.request` (`{ pluginId }`) on `PLUGIN_IO_TIMEOUT_MS` (`300_000ms`). If the preview row reports `outcome === "error"`, it returns `{ ok: false, reason }`; if `outcome === "local"`, it returns `{ ok: false, reason: "local directory plugin cannot be updated from a remote source — use Reload after editing" }`; if `outcome === "current"` or `outcome === "installed-newer"` (or carries no `proposal`), it returns `{ ok: true, update: { id: pluginId, previousCommit: currentRevision, currentCommit: currentRevision, updated: false } }`.
     2. When `outcome === "update"` and `proposal` is present, dispatches `plugin.source.update.apply.request` (`{ proposals: [proposal] }`) on `PLUGIN_IO_TIMEOUT_MS`. If the apply row reports `outcome === "error"`, it returns `{ ok: false, reason: row.error }`; when `outcome === "updated"`, it returns `{ ok: true, plugin: row.plugin, update: { id: pluginId, previousCommit: proposal.expected.revision, currentCommit: row.plugin?.installation?.currentRevision ?? row.plugin?.commit ?? targetCommit, updated: true } }`.
     3. The CLI fallback (`paseo --home <home> plugin update <pluginId> --yes --json`) parses both the structured `outcome: "updated" | "current" | "installed-newer" | "local" | "error"` schema and legacy `{ updated: boolean }` rows.
   - `pluginsManage` supports `pluginId: "paseo-factory" | "factory-burn-lab" | "factory-connector" | "factory-release-lab" | "all"` (where `"all"` applies only to `action: "update"`, updating all installed remote plugins with `updateAvailable === true`, or all remote plugins if none are cached, and always ordering `paseo-factory` **last** so companion updates finish before the Core plugin restarts).
   - **Core Self-Update / Self-Reload Lifecycle (`paseo-factory`):** Because `PluginService.updateSource("paseo-factory")` and `PluginService.reloadPlugin("paseo-factory")` stop the running `paseo-factory` worker before starting the new revision (causing `PluginRuntime` to reject the in-flight `factory.plugins.manage` RPC with `"Plugin stopped: paseo-factory"`), `FactoryShell` treats a `"Plugin stopped: paseo-factory"` (or transient connection drop during a Core `update` / `reload` or `Update All` that includes Core) as an expected **Core restart transition (`Reloading Core paseo-factory…`)** rather than a red failure, polling `factory.snapshot` until `corePlugin` reports `status === "running"` on the target revision (or surfacing a `statusDanger` error if `corePlugin.status === "failed"` / `corePlugin.error !== null` or the target revision fails to land within the restart window).
   - `pluginsManageSummary` inspects `reply.update` from `manageDaemonPlugin`: when `updated === true`, it returns `"updated <id> (<prevSha> → <currSha>)"`; when `updated === false`, it returns `"<id> is already up to date (<sha>)"`.

5. **Strict Daemon Home isolation.**
   - All plugin list, update-check, install, and manage calls execute strictly against the `home` of the Paseo daemon process hosting that `Factory surface` (`~/.paseo` in production Desktop vs `~/.paseo-factory` in trial runs), preserving the trial/prod boundary.

## Consequences

- `CONTEXT.md` updates **Factory surface** and **Companion plugin** to reflect the Core + 3 Companions `Plugins` view, two-phase `preview` → `apply` update protocol, graceful Core self-update restart tracking, per-card elapsed progress pills/labels, and persistent inline status/error banners.
- Every card in the `Plugins` tab stays compact (2 rows by default), clearly answers what version is installed (`vX.Y.Z · <sha>`), shows live per-card progress (`Updating <currSha> → <targetSha>… · Ns`) while an action runs, and records the final outcome or error inline without relying solely on ephemeral toasts.
