# 0031 — Idempotent Same-SHA Claims, Single-Active-Peer Law Across `Lead handoff`, and Role-Scoped MCP Isolation

- **Date:** 2026-10-27
- **Status:** Accepted
- **Amends:** ADR 0010 (`Accept` and `Task worktree` lifecycle), ADR 0011 & ADR 0016 (`Pi harness home` and `Role-scoped MCP bridge`), ADR 0013 & ADR 0027 (`Lead handoff` and Active Peer Roster), ADR 0015 & ADR 0019 (`Seat write fence` and `git_blocked` ingestion), ADR 0030 (`Claim` timeout alignment)

## Context

Forensic inspection of the live `profile-max` multi-wave run (`2026-10-26`, `T-01-foundation` through `T-07-verification`, with `Supervisor` on `antigravity/g-3-1-p:high`, `Lead` on `pi/openai-codex/gpt-6.1-sol:high`, and `Peer` on `pi/zai/glm-5.3:max`) exposed four operational failure modes across the `Lead` / `Peer` execution pipeline:

1. **Pi `builtin:mcp` 60-Second Client Timeout & Role MCP Bloat on `Supervisor` and `Lead`:**
   - Although ADR 0030 raised `DEFAULT_WAIT_MS` inside `plugin/bin/bridge.mjs` to `600_000ms` (`10m`), Pi's own MCP client (`@aliou/pi-mcp-adapter` / `builtin:mcp`) enforces a per-server client timeout (`serverConfig.timeout ?? DEFAULT_TIMEOUT_SECONDS`, where `DEFAULT_TIMEOUT_SECONDS = 60`). Because `writeMcpJson` in `src/pi-home.ts` omitted `"timeout"` on the `paseo_factory` and `zai-vision` entries in `<stateDir>/pi-agent/<role>/mcp.json`, Pi killed `agent_claim` at `60000ms` (`MCP error -32001: Request timed out`) whenever a Playwright e2e `Gate` took `62s–65s` (`T-05-campaign` seq 233, `T-07-verification` seq 306), and killed `mcp__zai-vision__ui_to_artifact` at `60000ms` even though `@z_ai/mcp-server` sets `Z_AI_TIMEOUT = "300000"` (`300s`).
   - Furthermore, `writeMcpJson` injected `zai-vision` and `context7` into all three roles (`supervisor`, `lead`, and `agent`) rather than only `agent` (`Peer`). In `paseo-room` and `codex-room`, `Supervisor` and `Lead` are coordination and diff-review seats that never call vision or third-party doc MCP tools.

2. **Duplicate Same-SHA `Claim`s After Client Timeouts & Unfenced `Accept` During an In-Flight `Gate`:**
   - When Pi's `60s` client timeout aborted the `Peer`'s `agent_claim` call on `T-07-verification` (`9719683`) at `60.0s` while the Spool's `Gate` finished `GREEN` `2.6s` later (`62.6s`, Attempt 1 `GREEN`, seq 306), the `Peer` retried `factory-claim` on the exact same commit `9719683`.
   - Because `factory.claim()` was not idempotent for an already-`GREEN` commit `sha` in the current `Contract epoch`, the retry opened a redundant `Attempt 2` (`gate_started` seq 307).
   - Simultaneously, `Lead` received the `Attempt 1 GREEN` mailbox notification and called `lead_accept_task("T-07-verification")` (seq 308). Because `factory.accept()` did not check `inFlightAttempt(history)` (unlike `factory.setContract()`), `accept()` landed the Task and deleted `/worktrees/T-07-verification` while `Attempt 2`'s Playwright `Gate` was actively running inside it — causing `Attempt 2` to crash with `ENOENT` (`gate_finished: red` seq 309) **after** `attempt_accepted` (seq 308) and flipping `projectTask()`'s projected `Verdict` on the `Accepted` Task from `green` to `red`.

3. **Multi-Peer Collisions in One `Task worktree` Across Re-Contracting and `Lead handoff` (`T-03-ranged`):**
   - On `T-03-ranged`, `Peer #1` (`33852156`) finished Attempt 1 `GREEN` (`2cdb4b7`). Outgoing `Lead` (`36e0a40e`) found a resize bug during diff inspection, called `lead_set_contract` (`18:24:32Z`) to open a new `Contract epoch`, and called `lead_spawn_agent` (`18:24:35Z`) to launch `Peer #2` (`1009fd8d`) in `/worktrees/T-03-ranged`.
   - Neither `contract_set` nor `spawn` canceled/archived the prior `Peer #1` (`33852156`), leaving both `Peer #1` (`idle`) and `Peer #2` (`running`) alive in the same worktree.
   - Outgoing `Lead` (`36e0a40e`) then crossed the `128,000` token mark and rotated via `Lead handoff` (`18:24:39Z` → `18:26:10Z`). Two bugs compounded during the handoff:
     1. `agentOfTask()` (`plugin/server/lead-mailbox.ts`) iterated over `daemon.agents.list` (which returns newest first, oldest last) and overwrote `matchedLive` on each match, binding the Task in the Active Peer Roster to the **older `idle` `Peer #1` (`33852156`)** instead of the **newer `running` `Peer #2` (`1009fd8d`)**.
     2. `completeHandoff()` immediately woke the successor `Lead` (`5a9cfa83`) even though `mailbox.jsonl` had zero queued items and `Peer #2` was still actively coding.
   - Seeing `agent 33852156 (live: idle) · no attempt yet` in its Turn-1 kickoff roster, successor `Lead` (`5a9cfa83`) called `lead_repoke_agent` (waking stale `Peer #1` to re-claim old commit `2cdb4b7`) and then spawned `Peer #3` (`bdbc0f7c`) and `Peer #4` (`b39be1f0`) into the same `/worktrees/T-03-ranged` directory while `Peer #2` was still editing files.

4. **Global Harness MCP `npx` Boot Blocks & Misattributed `git_blocked` Task Telemetry:**
   - When `Supervisor` ran on `antigravity` (`agy`), the Antigravity binary booted all global MCP servers configured in the user's `~/.gemini/antigravity/mcp_config.json` (`npx -y chrome-devtools-mcp`, `npx -y @notionhq/notion-mcp-server`). Because `Supervisor` runs with `PATH=<stateDir>/bin:...` and `PASEO_FACTORY_SEAT=supervisor`, `<stateDir>/bin/npx` (`exec-shim.mjs`) intercepted those startup `npx` calls and blocked them with `seat-write-fence` (`exit 126`), logging 6 `git_blocked` events.
   - Furthermore, `startGitBlockIngestion` (`plugin/server/choke.ts`) attached `task: contract.task` to any `git_blocked` event matching the Project root when only one unaccepted Contract was active, misattributing `Supervisor`'s 6 startup `npx` blocks at `<project-root>` onto `T-01-foundation`'s Task `choke` count (`choke: 6`).

## Decision

1. **Role-Scoped MCP Isolation & Explicit Pi `builtin:mcp` Server Timeouts (`src/pi-home.ts`, `src/roles-contract.ts`):**
   - Align with `paseo-room` and `codex-room`: in `writeMcpJson` (`src/pi-home.ts`), `supervisor` and `lead` receive **only** the `paseo_factory` MCP server in `<stateDir>/pi-agent/<role>/mcp.json`. External helper MCP servers (`zai-vision` and `context7`) are provisioned **strictly for `role === "agent"`** (`Peer`), and `src/roles-contract.ts` is updated accordingly.
   - Set explicit per-server `"timeout"` (in seconds) in `<stateDir>/pi-agent/<role>/mcp.json`: `"timeout": 600` (`10m`) on `paseo_factory` (matching `DEFAULT_WAIT_MS = 600_000` in `plugin/bin/bridge.mjs` and `DEFAULT_WAIT_SECS = 600` in `plugin/bin/factory-claim.mjs`) and `"timeout": 300` (`5m`) on `zai-vision` (matching `Z_AI_TIMEOUT = "300000"`).

2. **Idempotent Same-SHA `Claim`s in the Current Epoch & In-Flight `Gate` Guard on `Accept` (`src/factory.ts`, `src/task-state.ts`):**
   - In `factory.claim()` (`src/factory.ts`): if the current `Contract epoch` already contains a completed `GREEN` `Attempt` (`gate_finished` with `verdict === "green"`) for the exact same commit `sha`, return that `GREEN` `Attempt`'s result idempotently without opening a duplicate `Attempt` or re-running the `Gate`. (If the prior `Attempt` on that `sha` was `RED`, a retry continues to open a new `Attempt` below the `Attempt ceiling` so transient environment failures remain retryable.)
   - In `factory.accept()` (`src/factory.ts`): refuse with `gate-running` when an `Attempt` is currently in flight (`inFlightAttempt(history) !== undefined`), matching `factory.setContract()`, so `accept()` never archives the working `Peer` or deletes the `Task worktree` underneath a running `Gate`.
   - In `projectTask()` (`src/task-state.ts`): when a Task is `Accepted` (`acceptedAttempt !== undefined`), project the accepted `Attempt`'s `green` `Verdict` rather than allowing a post-accept ghost attempt to flip the projected `verdict` to `red`.

3. **Single-Active-Peer Law per `Task worktree` & Held `Lead handoff` While a `Peer` Is Running (`plugin/server/spool.ts`, `plugin/server/lead-mailbox.ts`):**
   - On `contract` (`lead_set_contract` / `factory contract`) for an existing Task in `plugin/server/spool.ts`: automatically cancel and archive any previously bound live `Peer` (`Agent`) sessions of that `(projectSlug, task)` so stale `Peer`s from a prior `Contract epoch` never remain alive in `idle` or concurrently edit the shared `Task worktree`.
   - On `spawn` (`lead_spawn_agent` / `factory run`) in `plugin/server/spool.ts`: if a bound `Peer` for that `(projectSlug, task)` is currently actively running (`status === "running" || status === "initializing"`), refuse the duplicate `spawn` (`spawn_refused`, `reason: "peer-already-running"`) with an explanatory message instructing `Lead` to wait for the active `Peer` (or call `lead_set_contract` first to start a new epoch); if any prior bound `Peer` for that Task is stopped (`idle` or `error`), cancel and archive it before spawning the replacement `Peer`.
   - In `agentOfTask()` (`plugin/server/lead-mailbox.ts`): fix the `livePeers` resolution order so `running` / `initializing` `Peer`s and the newest live `Peer` in the current `Contract epoch` take precedence over older `idle` `Peer`s at the tail of `daemon.agents.list`.
   - In `completeHandoff()` and `drainLeadMailbox()` (`plugin/server/lead-mailbox.ts`): when `Lead handoff` completes while an unaccepted Task's `Peer` is actively running (`driverWaveInFlight` or a live `running`/`initializing` `Peer`) and `state.queued.length === 0` (no pending mail in `mailbox.jsonl`), keep `pendingHandoffByAgentId` held instead of waking the successor `Lead` into an empty wait state; deliver the `pendingHandoff` kickoff bundle together with the `Peer`'s terminal `Verdict` (or `Needs-human` / escalation) mail turn when the `Peer` finishes.
   - Because a `Peer` wave may run longer than Paseo's 1-hour idle-runtime collection threshold (which unloads inactive seats to `status === "closed"` with `archivedAt === null`), `drainLeadMailbox` and `drainSupervisorMailbox` treat both `status === "idle"` and `status === "closed"` (when `!isBlockedByAttention(seat)`) as ready for mail (`isSeatReadyForMail`), allowing `daemon.agents.ref(id).send(prompt)` to wake a `"closed"` seat automatically; additionally, interactive `Lead` / `Supervisor` resume events on `server.before("agent.session_open")` schedule a mailbox pump, `notifyPeer` scopes `driverWaveInFlight(projectEventsOf(resolved.root), liveAgents)` to the owning Project, `completeHandoff` always persists the resolved `handoffText` to `<projectStateDir>/lead-handoff.md` so `drainLeadMailbox` can durably reconstruct `pendingHandoff` on Turn 1 of an unstarted successor `Lead` (`lastUserMessageAt == null`) after a daemon/plugin restart, and `injectSessionEnv` ensures an empty directory stub exists when resuming an archived `Peer` whose `Task worktree` was removed after `Accept` so `PiRpcAgentClient.resumeSession` never fails with `spawn pi ENOENT`.

4. **MCP Stdio Server `npx` Passthrough & Strict `git_blocked` Task Attribution (`src/choke.ts`, `plugin/bin/exec-shim.mjs`, `plugin/server/choke.ts`):**
   - In `isPackageMutationSegment` (`src/choke.ts`) and `plugin/bin/exec-shim.mjs`: allow `npx` invocations that launch read-only MCP stdio server packages (`@z_ai/mcp-server`, `@upstash/context7-mcp`, `chrome-devtools-mcp`, `@notionhq/notion-mcp-server`, `@modelcontextprotocol/server-*`, or packages matching `(^|\/)(mcp-[a-z0-9_-]+|[a-z0-9_-]+-mcp(-server)?|server-[a-z0-9_-]+)(@|$)`) so harnesses booting global user MCP configs do not trigger `seat-write-fence` exit-126 blocks at startup, while keeping all package-mutating and project-scaffolding `npx` commands blocked on `Supervisor` and `Lead`.
   - In `startGitBlockIngestion` (`plugin/server/choke.ts`): bind `task: contract.task` on a `git_blocked` Ledger event strictly when `isContractedAgentCwd(factory, record.cwd)` is true and `record.rule` is not a seat fence rule (`seat-write-fence`, `supervisor-git-fence`, `lead-git-fence`), so `Supervisor` or `Lead` fence blocks at `<project-root>` are recorded at project level (`task: undefined`) and never pollute an active Task's `choke` counter.

## Consequences

- **Positive:**
  - Long Playwright/e2e `Gate` runs (up to `10m`) and `zai-vision` calls (up to `5m`) on Pi `Peer`s no longer fail prematurely at `60000ms` with `MCP error -32001: Request timed out`.
  - `Supervisor` and `Lead` on Pi have a minimal, distraction-free MCP tool surface (`paseo_factory` only), matching `paseo-room` and `codex-room`.
  - Duplicate `Claim` retries on an already-`GREEN` commit `sha` return idempotently without re-running the `Gate`, and `Accept` can never race an in-flight `Gate` or delete its `Task worktree` mid-run.
  - At most one active `Peer` ever operates in a `Task worktree` at a time, and `Lead handoff` at `128k` preserves seamless continuity with an in-flight `Peer` without waking the successor `Lead` prematurely or re-poking stale `Peer`s.
  - Harnesses like Antigravity (`agy`) boot global user MCP servers cleanly without `seat-write-fence` noise, and Task `choke` telemetry strictly reflects the Task `Peer`'s own blocked commands.
- **Negative / Trade-offs:**
  - If a `Peer` wants to force a fresh `Gate` run after a `GREEN` `Attempt` in the same `Contract epoch`, it must create a new commit `sha` (or `Lead` must open a new `Contract epoch` via `lead_set_contract`), which matches the invariant that a `GREEN` `Attempt` at a fixed commit `sha` under an unchanged `Contract` is already verified.
