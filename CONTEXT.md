# paseo-factory

A verification line for coding agents: the work is judged against criteria fixed before
it starts, by running checks rather than trusting the agent's word, and every step is
recorded so it can be read back later.

## Language

### People and parties

**Agent** (or **Peer** / **Scrum role**):
The working agent (`factory-peer` provider in Paseo's `config.json`, tab titled `Peer · <Task>` in `slp` mode or `PM · <Task>`, `UX · <Task>`, `Arch · <Task>`, `Dev · <Task>`, `QA · <Task>` when contracted with a `Scrum role` in `scrum` mode, ADR 0017, ADR 0032) doing the work on a Task inside its isolated Task worktree, equipped with the `agent` role slice of the Role-scoped MCP bridge (`agent_claim`, `agent_escalate_blocker`) and the `factory-claim` CLI (ADR 0016). It may make Claims; it never sets or changes a Contract. Under ADR 0029 and ADR 0032, it implements only its bounded outcome (or autonomous BMad V7 role deliverable under `.scratch/<slug>/`), records decisions and assumptions in its owned `.scratch/<initiativeId>/decisions/<task>.jsonl` rather than stopping for interactive prompts, and respects Excluded / Deferred to Later Waves. After a third failed fix with the same symptom it stops local patching to diagnose the root mechanism, or commits independent completed work and escalates with concrete evidence and the current SHA via REOPEN_REQUEST (foundation | dependency | lifecycle | API | ownership | verification), DEPENDENCY_REQUEST, or BLOCKED.
_Avoid_: worker (except as the legacy `lanes.json` key), bot

**Scrum role**:
One of `pm | ux | architect | dev | qa`, specializing working Agent authority (`agent`) through a persisted `execution?: ScrumTaskBinding` on the Contract (ADR 0032, ADR 0049). PM delivers PRD; UX delivers DESIGN, EXPERIENCE and offline mockups; Architect delivers architecture with evidenced Stack and stable AD rules; Dev delivers one bounded story with Tier-1 slice self-checks, modular per-slice test files (`tests/<slice>.*`) with explicit timeouts, Anti-Whack-a-Mole stopping after a 3rd repeated symptom, and a `Recurrence Guard` sibling sweep on fix Tasks; QA delivers a regression bundle and structured evidence — mandatorily executing Tier-2 cross-module integration and Tier-3 cold-start entrypoint smoke verification before `qa.audit` can report `passed` — without modifying product source or existing assertions. Each Task owns a separate `decisions/<task>.jsonl`. Stable IDs may have gaps and deprecated definitions; references are distinct from definitions. A missing binding always means SLP/Peer, regardless of current Project mode.
_Avoid_: standing specialist seat, specialization as authority, interactive BMad menus, passing QA audit without cold-start entrypoint smoke evidence

**Owner**:
Whoever sets or ratifies the work's outcome and final acceptance — the human, or a seat the human has delegated authority to (the Supervisor as conversational delegate; the Lead for intermediate Task contracts and clean green-task acceptance under ADR 0010, with Human override always retained). Never the Agent working that Task.
_Avoid_: reviewer, user

**Supervisor**:
The Owner's conversational delegate seat for a Project (`labels: { seat: "supervisor", project: <slug> }`, tab titled `Supervisor`), rooted at the Project's directory (`cwd = <project-root>`, bound to the Project's active main Paseo `workspaceId` via a 2-step seat launch and initialized on Turn 1 with a deterministic Seat kickoff packet, ADR 0010, ADR 0015, ADR 0016, ADR 0017) rather than an external `<home>-supervisor` folder, with compaction-proof role instructions written from a single shared role-contract module (`src/roles-contract.ts`) to both `config.systemPrompt` and `<stateDir>/pi-agent/supervisor/APPEND_SYSTEM.md`, equipped with the `supervisor` slice of the Role-scoped MCP bridge (`supervisor_dispatch_lead`, `supervisor_accept_task`, `factory_status`, ADR 0016) alongside the `factory` CLI, and 100% of the Owner's slash commands and skills preserved via symlinked `~/.pi/agent/{prompts,skills}` (ADR 0013, ADR 0015) while `<project-root>/AGENTS.md` is never overwritten. It clarifies intent (`grilling`), diagnoses reported repository states via read-only inspection (`ls`, `cat package.json`, `git status`, `git log`) before immediately dispatching any required fix, dependency installation, or verification wave to the Project's Lead via `supervisor_dispatch_lead` / `factory lead dispatch` (immediately ending its turn to wait for the Lead's report, ADR 0019), receives completion summaries and escalations through the bidirectional `mailbox.jsonl` (`to: "supervisor"`, ADR 0015), relays status, verdicts and needs-human items to the Owner, accepts on the Owner's word (`accepted_by: "supervisor"`), and curates project-level rules in `AGENTS.md` / `CONTEXT.md`. Enforced by the Spool and the 3-layer `Seat write fence` (ADR 0015, ADR 0016, ADR 0019), the Supervisor never decomposes Tasks, never calls `factory contract` or `factory run`, never edits product source files or runs package-mutating or git-committing commands on `<project-root>`, never calls Paseo's native agent-management tools directly, never pushes externally, and never accepts without the Owner's word. Added in v0.0.9 (ADR 0006); scoped per Project at `cwd` in ADR 0010; made compaction-proof in ADR 0013; fenced and wired bidirectionally in ADR 0015; equipped with the Role-scoped MCP bridge, Seat kickoff packet, and 3-layer execution fence in ADR 0016; unified with Lead in the Project's main Workspace with orphan workspace sweeping in ADR 0017; equipped with the Diagnostics & Run-Verification Law and Layer-3 package-manager shims in ADR 0019. Under ADR 0029, it transmits Owner outcomes, boundaries, and verification criteria faithfully, preserving architecture freedom unless the Owner explicitly requests file-packaging constraints, and challenges architectural traps or packaging anti-patterns (such as forcing a multi-subsystem application into a single file) via `grilling` with a recommended modular alternative before dispatching unless the Owner explicitly confirms running as-is.
_Avoid_: manager, orchestrator, assistant (and Driver — a mechanism, not a seat)

**Lead** (or **Scrum Lead / PO** in `"scrum"` mode):
The presiding technical seat over Agents for a Project (`labels: { seat: "lead", project: <slug> }`, tab titled `Lead` in `"slp"` mode or `Scrum Lead` in `"scrum"` mode, `cwd = <project-root>`, co-located inside the active `Supervisor`'s Paseo `workspaceId` with `parent: supervisorId` when a Supervisor is live via a 2-step seat launch and initialized on Turn 1 with a deterministic Seat kickoff packet, ADR 0010, ADR 0015, ADR 0016, ADR 0017, ADR 0032): a standing model-backed Paseo agent on the selected workflow's `lead` lane (`lanes.json` for SLP, independent `scrum-lanes.json` for Scrum, anchored by the unified role contract in `config.systemPrompt` and `<stateDir>/pi-agent/lead/APPEND_SYSTEM.md`, equipped with the `lead` slice of the Role-scoped MCP bridge — `lead_set_contract`, `lead_spawn_agent`, `lead_accept_task`, `lead_repoke_agent`, `lead_needs_human`, `lead_report_to_supervisor`, `factory_status` — alongside the `factory` CLI, receiving work through the Project's Lead mailbox, and rotatable manually or automatically via Lead handoff at the `128,000` token mark, ADR 0013, ADR 0015, ADR 0016, ADR 0047) paired with the Driver's deterministic watch/respawn/ceiling rider underneath. The Lead reads the Seat kickoff packet and repository, splits a Supervisor directive into one or more Tasks (delivering vertical user-facing journey slices after at most 1–2 foundational setup waves rather than horizontal chains of backend-only micro-waves, writing concise `<= 2,500`-char 4-Part Briefs that state outcome, boundary contracts, exclusions, and Gate command without pre-solving internal helper signatures or mandating N unit-test files per task, and never reading implementation or framework `SKILL.md` files into its own context window, ADR 0044, ADR 0047), sets each Task's Contract around desired outcomes, regression invariants, and a Gate command that runs both the new verification and the repository's existing test/build suite (without pre-declaring file-scope handcuffs for the Peer, ADR 0028), spawns working Agents in isolated Task worktrees, judges hand-backs strictly against mechanical Gate evidence and its own direct inspection of the attested commit diff (`git show --stat "<sha>"` and bounded per-file `git diff "<sha>^" "<sha>"` without JSON-stringifying multi-file outputs inside a single REPL call, plus the proof falsification check, without running ad-hoc out-of-band shell/node scripts to invent uncontracted edge cases after a GREEN Gate, ADR 0029, ADR 0030, ADR 0044, ADR 0047), accepts clean green Tasks in every wave (`accepted_by: "lead"`, when Verdict is green and the Task is not in `Needs-human`, ADR 0030, ADR 0044), re-briefs or escalates stuck work (`needs_human`), and reports final landed completion or human questions back to the Supervisor via `lead_report_to_supervisor` / `factory supervisor report` (`to: "supervisor"` in `mailbox.jsonl`, ADR 0015, ADR 0016). Under ADR 0032 and ADR 0049, Scrum Lead uses an independent renderer and frozen Scrum roster, receives the unified `Seat kickoff packet` (`omitSystemPromptDuplicates: true`) with `<projectStateDir>/notebook.md` and a bounded `formatScrumRunDigest(activeRun)` (never a duplicate `renderScrumPrompt` or raw `JSON.stringify(activeRun)` dump), chooses a scale-adaptive track, and records readiness against exact landed artifacts. UX/Architect may work in parallel only with disjoint ownership and a landed shared foundation. Contradictions or unsafe assumptions block Dev. UI decisions are persisted against exact revision/digest through Supervisor; accepted UX revisions remain closed. Scrum Lead enforces the same Peer-Owned Domain Skills Law, bounded per-file diff review (`<= 6,000` tokens), proof falsification check, context-ceiling recovery (`peer-handoff-<task>.md`), and `Recurrence Guard` / `Wave Hardening` in `<projectStateDir>/notebook.md` as SLP Lead. QA delivers a GREEN regression artifact (including Tier-2 cross-module integration and Tier-3 cold-start entrypoint smoke proof) that may report product defects; Dev promotes unchanged tests through bounded fix or verification Tasks with a sibling sweep, and a fresh re-audit proves the current executable revision. Structured completion requires the Scrum controller's separate predicate. These orchestration rules do not change SLP acceptance.
_Avoid_: manager, foreman, orchestrator, "the loop" (that names the mechanism), Driver (a mechanism, not a seat)

### Work and criteria

**Execution mode**:
The Project's selected `slp | scrum` workflow in its independent `execution.json` with schema version and monotonic revision. Existing Projects without metadata always use SLP. Machine selection affects future registrations only. Mode switching is an idle Owner operation with durable seat-transition recovery; pending Tasks, Agents, Gates, directives, handoff or nonterminal Scrum runs block switching. A Scrum run freezes policy, roster, approval settings, track and finite budgets. Task identity comes from its Contract binding, never mutable selection.
_Avoid_: mode inside SLP lanes, implicit migration

**Owner wait**:
A recorded wait for an explicit decision or answer from the Owner, including UI design review, that remains pending until the Owner responds or explicitly cancels the work and prevents only work dependent on that answer. Owner absence does not expire the wait; a provider failure or unexplained Agent silence is not an Owner wait.
_Avoid_: approval timeout, Agent stall, provider outage

**Task allowance**:
The cumulative number of Tasks authorized for a Scrum run, including UX revision Tasks, which the Owner may explicitly increase without replacing the run or erasing its consumed allowance. Distinct from a Task's Attempt ceiling and the run's automatic QA fix-round limit.
_Avoid_: time budget, retry allowance, automatic reset

**Owner allowance grant**:
An explicit Owner authorization to add a finite amount to a Scrum run's Task allowance or, separately, its automatic QA fix-round allowance, retaining the work already consumed. It grants capacity, not acceptance, design approval or permission to bypass other unresolved decisions.
_Avoid_: budget reset, automatic replenishment, approval waiver

**UI Design Approval Checkpoint**:
A Scrum-only durable decision on exact accepted design revision, artifact commit and SHA-256 digest. Supervisor relays the Owner's explicit approved, changes_requested or waived decision; Lead and Agents cannot self-approve. Readiness and browser evidence remain required. Changes requested create a new UX revision Task, preserving accepted history. The existing `supervisor_report` / `report` envelope carries optional `reportType: "ui-review"` and a structured preview identity. Approval does not itself establish readiness or product completion.
_Avoid_: chat-keyword approval, reopening accepted UX Tasks

**Project**:
One Git repository supervised by the factory, identified canonically via `git rev-parse --show-toplevel --git-common-dir` as `<project-slug> = <basename>-<sha1(gitRoot).slice(0,6)>` (ADR 0010). Starting a `Supervisor` or `Lead` seat or adding a Project on an existing non-Git directory automatically initializes a Git repository with an initial empty commit so per-Task worktrees work immediately, and registers the Project (ADR 0024). Owns its isolated state directory (`<stateDir>/projects/<project-slug>/`) and its own `Factory` instance in the plugin server's per-Project registry (`factoryForProject(slug)`, ADR 0045), containing its registration (`project.json`), per-Project `Ledger` (`ledger.jsonl`), `Reports` (`report-<task>-<attempt>.md`), `Gate` logs (`gate-<task>-<attempt>.log`), `Retro` proposals (`retro-<YYYY-MM-DD>.md`), and `Task worktrees`, plus its standing `Supervisor` and `Lead` seats — giving each Project an independent `Task` ID namespace (`T-01`, `T-02`, ...) and isolated `seq` stream (`1..N`), with one-time automatic startup migration (`migrateRootLedgerToProjects`) splitting and compacting any legacy root `<stateDir>/ledger.jsonl` into per-Project directories and archiving the legacy root files to `<stateDir>/archive/legacy-root-<timestamp>/` (ADR 0045). If the Project's directory is later deleted on disk, the registered Project remains selectable by its persisted identity (`missingRoot`) so its history can be inspected or purged via `Project delete` (ADR 0024).
_Avoid_: workspace (that is the working copy a Task runs in), folder, team, shared root `ledger.jsonl` across multiple Projects

**Task**:
One unit of work within a Project, identified by a filename-safe id, judged against exactly one Contract.
_Avoid_: job, ticket, lane

**Contract**:
The done-criteria for a Task, fixed before the Agent starts: one Gate command, optional immutable `execution?: ScrumTaskBinding` (Scrum run, role, policy/config revisions and artifact refs; absence always means SLP/Peer, ADR 0032), optional Artifact path (omitted when the Gate command and commit diff suffice, ADR 0028), optional `scope` (used only as an explicit opt-in when a Task is contracted to edit a root memory file `AGENTS.md`/`CLAUDE.md`/`CONTEXT.md`, never as a Station 4 red Verdict handcuff on code files, ADR 0028), and optional required `skills`, rooted at a Project workspace. Setting a new Contract (`contract_set`) on an unaccepted Task (including one currently in `Needs-human` or at the `Attempt ceiling`) opens a fresh Contract epoch, resetting the Task's Attempt counter, clearing prior `Needs-human` status, and canceling/archiving any previously bound live `Peer` (`Agent`) sessions of that Task so stale `Peer`s from a prior epoch never linger in `idle` or concurrently edit the shared `Task worktree`, while preserving all prior Ledger events, the Task's live `Task worktree` on disk, and its original `base` commit when `base` is omitted (ADR 0018, ADR 0019, ADR 0028, ADR 0031). Lead-authored descriptions have four explicit parts: Bounded Outcome, Contract Boundary & Regression Invariants, Excluded / Deferred to Later Waves, and Verification (the exact Gate command), anchored just-in-time to the current Stable Checkpoint and capped at `<= 2,500` chars without pre-solving internal function/prop names from deep implementation files (ADR 0029, ADR 0032, ADR 0047).
_Avoid_: spec, acceptance criteria, hợp đồng (outside research notes)

**Workspace**:
The git working copy a Task's work lives in; the Gate runs there and the Artifact is resolved inside it. Under ADR 0010, each spawned Task runs inside its own isolated Task worktree so the Project's root checkout stays clean.
_Avoid_: repo, project dir, cwd

**Serial Wave**:
A bounded stage of a directive, normally one cohesive vertical-slice Task owning a single new interactive workflow or subsystem (real screen/UI + state/data wiring + journey test, after at most 1–2 foundational setup waves for app shell and core schema/repository seam, ADR 0044). Initial roadmaps are rolling-wave outlines rather than fixed commitments: after each wave lands at a Stable Checkpoint, Lead re-evaluates actual repository complexity and splits any downstream wave that spans multiple user journeys before contracting it, without decomposing work into horizontal chains of backend-only micro-waves (`T-04c1..c6`, ADR 0044). Multiple Tasks share a wave only when the existing foundation is stable and their module/file surfaces are genuinely disjoint. Each wave is accepted before the next is contracted (ADR 0029, ADR 0034, ADR 0044).
_Avoid_: all-at-once decomposition, locked upfront multi-wave roadmaps, multi-subsystem mega-tasks, horizontal backend-only micro-wave chains

**Stable Checkpoint**:
The landed Project HEAD established by Acceptance of a GREEN wave; the foundation for the next wave's Contracts, Task worktrees, and in-flight `Wave Hardening` (ADR 0029, ADR 0030, ADR 0048).
_Avoid_: unaccepted green commit

**Wave Hardening**:
The Lead's in-flight workflow self-correction at a `Stable Checkpoint` boundary whenever a costly failure mechanism (RED `Gate`, `re-contract`, or `Choke` denial) triggers the `Recurrence Guard` (`observed → recurred`, ADR 0048). Rather than deferring workflow potholes to a passive backlog or waiting for an end-of-project `Retro` ceremony, the Lead applies at most one highest-leverage fix before contracting the next `Serial Wave`, following the 3-tier hardening hierarchy: (1) mechanical `Gate` check, script, or `.worktreeinclude` update applied immediately in-flight; (2) a concise 1-line navigation pointer quoted into downstream `Contract`s and proposed at directive completion in the 4-line Owner ratification format for `<project-root>/AGENTS.md` or `CONTEXT.md`; (3) deprecation and mechanical replacement of any existing `AGENTS.md` prose rule that a `Peer` still violated (`no-op` pruning).
_Avoid_: backlog deferral, waiting for a manual retrospective ceremony while downstream `Peer`s repeat the same failure, adding multi-paragraph prose warnings to `AGENTS.md`

**Recurrence Guard**:
The two-strike causal filter (`observed → recurred → hardened → verified`, tracked in `<projectStateDir>/notebook.md`, ADR 0048) governing when a workflow failure earns a structural change. A first occurrence is recorded as `observed` with its causal mechanism (`Cause → Effect`) and evidence (`Task` + `seq`) without adding repo-wide rules; a second occurrence of the same mechanism moves the row to `recurred` and triggers `Wave Hardening` (or a `Retro` `Proposal` citing at least two distinct `seq`s); once the fix holds across subsequent waves, the row is marked `verified` and folded or pruned within the notebook's `80`-line ceiling.
_Avoid_: "seen twice" (informal), one-off rule bloat from a single surprise, unverified slogan rules

**Project notebook**:
The Lead's bounded (`<= 80` lines / `<= 4 KB`) per-Project operational memory file at `<projectStateDir>/notebook.md` (`~/.paseo/plugin-state/paseo-factory/projects/<slug>/notebook.md`, ADR 0048, ADR 0049), stored outside `<project-root>` so it never dirties the Git working tree or pollutes `Peer` (`Agent` / `Scrum role`) context windows. Contains two fixed sections — `## 1. Verification & Run Recipe` (`Worktree & Env Setup`, `Fast Slice Check`, `Full Cumulative Gate`, `Process & Port Cleanup`) and `## 2. Recurrence Guard` — and is automatically embedded into both `SLP` and `Agile Scrum` `Lead` and `Supervisor` kickoff packets (`buildSeatKickoffPacket`) so institutional run knowledge survives `128,000`-token `Lead handoff` rotations and is wiped cleanly on `Project reset`.
_Avoid_: dumping Lead orchestration rules into `<project-root>/AGENTS.md` where every `Peer` pays context pressure to read them, untracked files inside `<project-root>`

**Contract epoch**:
One version of a Task's Contract and the Attempts judged against it. Re-contracting begins a new epoch; an Attempt number identifies work within that epoch.
_Avoid_: retry cycle, Task version

**Task worktree**:
The linked `git worktree` automatically allocated for a Task at Spawn under `<projectStateDir>/worktrees/<task>` on branch `factory/<task>` (rooted at the Contract's `base` commit, copying `.worktreeinclude` entries and symlinking `<project-root>/node_modules` when present, and registered in Paseo under the Project's own `projectId` with the human-readable Workspace title `Peer · <Task> — <short summary>` rather than an internal `<slug> <task>` hash, ADR 0010, ADR 0015, ADR 0017, ADR 0019). Preserved across in-place `contract_set` re-contracting of an unaccepted Task (`worktreeFor` and `liveContractFor` retain the latest unaccepted `spawn_dispatched.worktree` while it exists on disk, ADR 0019), isolates the working Agent (created with `parent: leadAgentId` and tab title `Peer · <Task>`) and Gate execution from `<project-root>`, hydrates `<project-root>/node_modules` from `<worktree>/node_modules` when `<project-root>` lacks installed dependencies, lands its `claimedCommit` back into `<project-root>`'s local branch upon Acceptance, automatically reaps any leaked test or dev-server child processes (`@embedded-postgres`, Playwright/Chromium, etc.) whose command line references `<worktree>` before removing or resetting the worktree directory (`reapWorktreeProcesses`, ADR 0044), and automatically archives both the working Agent and the temporary Paseo worktree workspace before removing the directory (ADR 0015, ADR 0019, ADR 0044). For a pre-contracted Task with no Claims in its current Contract epoch, an Acceptance recorded after that Contract advances initial allocation to current project HEAD instead of its stale base; retries with current-epoch Claims retain the contracted base (ADR 0029).
_Avoid_: clone, sandbox, shadow copy

**Workspace conflict**:
Two live Contracts whose execution Workspaces nest inside one another (`inside` / `contains`), or two live Contracts on the same Project that both explicitly declare overlapping `scope` globs. Because every Task executes in its own isolated `Task worktree` and merges through `landTaskWorktree` at Acceptance, unscoped Contracts on the same Project root never conflict at contract or spawn time (ADR 0028). Added in v0.0.5; updated in ADR 0010 and ADR 0028.
_Avoid_: scope conflict (the charted name — the real key is workspace overlap, not scope intersection), merge conflict

**Gate**:
The command named in a Contract whose exit status is the factual check of the work, executed in its own detached OS process group (`detached: true`, ADR 0016) so that when the command exits or times out, any leftover descendant child processes are reaped (`SIGTERM` → `SIGKILL` on `-pgid`) before stream closure is awaited.
_Avoid_: test step, check, cổng (outside research notes)

**Artifact**:
An optional workspace-relative path inside the Workspace that, when specified on a Contract, must exist for a Verdict to be green (ADR 0028). It can never point outside the Workspace.
_Avoid_: deliverable, output file

### Judging

**Claim**:
The Agent's statement that a Task is finished at a specific commit. A Claim is evidence of intent, never of completion. Within the current `Contract epoch`, if a completed `GREEN` `Attempt` already exists for the exact same commit `sha`, a duplicate `Claim` on that `sha` returns the existing `GREEN` `Attempt` idempotently without opening a redundant `Attempt`, re-running the `Gate`, or re-emitting duplicate `Meter` / `Lead mailbox` verdict hooks (`outcome.gate.seq <= admitted.priorSeq` in `plugin/server/spool.ts`), whereas a retry on a `sha` whose prior `Attempt` was `RED` opens a new `Attempt` below the `Attempt ceiling` (ADR 0031).
_Avoid_: "done" (for the Agent's side), report, submission, duplicate `mail_queued` verdict notifications on idempotent `Claim` retries

**Attempt**:
One Claim and the Gate run it triggers. A Task may have up to three Attempts (the Attempt ceiling, ADR 0008); they are numbered and never overlap.
_Avoid_: retry, run, iteration

**Verdict**:
The factory's red/green judgment of one Attempt. Green means the Workspace sat clean at the claimed commit both before and after the Gate, the Gate exited 0, any Contract-specified Artifact exists, and no root memory file (`AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`) was modified without an explicit Contract opt-in (ADR 0028). Green is evidence, not acceptance.
_Avoid_: result, status, pass/fail

**Accepted**:
The state of a Task after one of its green Attempts is accepted (`attempt_accepted`, recording `accepted_by: "owner" | "supervisor" | "lead"`, refused with `gate-running` whenever an `Attempt` is currently in flight so Acceptance never archives the working `Agent` or removes the `Task worktree` underneath a running `Gate`, and always projecting the accepted `Attempt`'s `green` `Verdict` in `projectTask`, ADR 0010, ADR 0031) and its claimed commit is landed into the Project's local checkout from the Task worktree (hydrating `<project-root>/node_modules` when needed, preserving `factory/<task>` if a local merge conflict requires resolution, and permitting an idempotent re-`accept` on a `pending-conflict` Task to complete `landed` once the conflict is resolved; never pushing to remote, ADR 0010, ADR 0019). Under ADR 0030, the Lead accepts green Attempts in every wave, including the final wave, whenever Verdict is green and the Task does not stand in `Needs-human`, after inspecting `git show --stat "<sha>"` and `git diff "<sha>^" "<sha>"` in the Closure & Integration Loop. The Owner retains override and final sign-off.
_Avoid_: done, finished, complete, passed

**Fresh-eyes review** _(retired in ADR 0030)_:
A historical pre-Lead headless review step (`fresh_eyes_written`, added in v0.0.2 / ADR 0005 when no model-backed `Lead` seat existed, unlocked onto `lanes.json` in ADR 0009, and smart-defaulted in ADR 0018). Retired from the active `Contract` / `Claim` / `Acceptance` execution pipeline in v0.0.49 (ADR 0030) in favor of canonical 2-party SLP separation (`Peer` + mechanical `Gate` + `Lead` inspecting `git show --stat "<sha>"` and `git diff "<sha>^" "<sha>"` in the Closure & Integration Loop, matching `paseo-room` and `codex-room`). Historical `fresh_eyes_written` events and `contract_set.freshEyes` fields in existing `Ledger` files remain readable for backward-compatible history projection, never blocking `Lead` acceptance.
_Avoid_: mắt soi (outside research notes), code review, self-review

**Watch**:
The record-only post-verdict pass that asks the Watch questions about one Attempt — a model prompted headless and tool-less on the Watch's configured lane (Lane config, defaulting to `pi/zai/glm-5.3` or `copilot/gpt-5.4`, ADR 0009) reading the run timeline, the Contract, the diff and the gate output in one strict-answer pass — and appends exactly one ledger line (`watch_written`). A passenger, never a judge: no notification, no escalation, and Verdicts and driver exits are unchanged by its answers. Off unless the Contract marks it on. Added in v0.0.6; the question table shrank to four in v0.0.7, returned to five in v0.0.8, and moved from a hardcoded Copilot pin to the Lane config in v0.0.13.
_Avoid_: watcher, monitor, alarm, "Jev" (historical: the v0.0.6 design first used a decision model, dropped for the Copilot subscription before the first run)

**Watch question**:
One of the five fixed yes/no questions the Watch asks (destructive-writes, test-weakened, stuck-loop, scope-creep, secret-leak) — each with fixed wording and true/false criteria, answered as a probability between 0 and 1 in a strict `name: probability` answer format, never prose. The v0.0.7 shrink kept four of the original eight (fake-done, unverified-claims and self-accept dropped); destructive-writes returned in v0.0.8, its battery arm redesigned so the blocked step rides a task that still reaches a Claim — the v0.0.6 arm stalled on the block and left the Watch nothing to read.
_Avoid_: check, heuristic, alert rule

**Retro**:
The on-demand, Owner-invoked, strictly per-Project fresh-context audit pass over a single Project's recorded history (`<stateDir>/projects/<project-slug>/ledger.jsonl` and `<projectStateDir>/notebook.md`, ADR 0045, ADR 0048) — complementing in-flight `Wave Hardening` when the Owner wants to audit historical runs. Reads the Project's deduplicated per-task Ledger digest (carrying only the latest `contract_set` description per Task while keeping earlier superseded `contract_set` events as compact 1-line `seq` headers, and deduplicating `report_written` paths before reading reports so each Attempt report is embedded at most once, ADR 0045), every Report of that Project, its red Attempts' gate logs, and `<projectStateDir>/notebook.md` — in which a model prompted headless and tool-less on the Retro's configured lane (Lane config, ADR 0009, stripping optional Markdown JSON code fences before parsing proposals, ADR 0045) proposes at most the top 1–2 highest-impact `Gate` checks or `Contract`/`AGENTS.md` pointers for patterns meeting the `Recurrence Guard` threshold (each `Proposal` citing at least two distinct ledger `seq`s, ADR 0048). Refused when no specific Project is selected (`retro-project-required`, disabled in the `"All projects"` UI view, ADR 0045). Appends exactly one advisory ledger line (`retro_written`) and writes one proposals file (`<projectStateDir>/retro-<YYYY-MM-DD>.md`) in the 4-line Owner ratification format; never applies, judges, or notifies. Nothing becomes law until Ratification. Added in v0.0.7; unlocked onto the Lane config in v0.0.13; scoped per-Project and deduplicated in ADR 0045; aligned with `Recurrence Guard` and `<projectStateDir>/notebook.md` in ADR 0048.
_Avoid_: retrospective (the agile ceremony), postmortem, session debrief, "Retro pass" (the mechanism is the noun, like Watch), cross-Project global Retro dumps, primary in-flight error recovery (that is `Wave Hardening`)

**Proposal**:
One unit of `Wave Hardening` or `Retro` output requiring Owner ratification: a class (`gate-check`, `contract-draft`, or `observation`), the recurring task and ledger `seq` evidence that grounds it (`Recurrence Guard`), the causal mechanism, and the exact preview diff for `<project-root>/AGENTS.md`, `CONTEXT.md`, or verification scripts (rendered in the 4-line Owner ratification format, ADR 0048). Advice for the Owner — the factory never applies repo-memory proposals without the Owner's nod. Added in v0.0.7; updated in ADR 0048.
_Avoid_: finding (a fresh-eyes word), recommendation, one-off single-seq complaints

**Ratification**:
The Owner's act of adopting a `Proposal` (from `Lead`'s end-of-directive report via `Supervisor` or from an on-demand `Retro` pass) into tracked repository files (`AGENTS.md`, `CONTEXT.md`, `docs/adr/`, or `Gate` scripts); recorded in the repo, never a factory event. While in-flight Tier-1 `Gate`, `.worktreeinclude`, and `Project notebook` hardening is applied immediately by `Lead` at `Stable Checkpoint` boundaries without blocking the run, edits to tracked repository memory (`AGENTS.md`, `CONTEXT.md`) always wait for Ratification (ADR 0048). Added in v0.0.7; updated in ADR 0048.
_Avoid_: acceptance, approval (Accepted is the Attempt word), unratified agent edits to `AGENTS.md` / `CONTEXT.md`

**Flaw battery**:
A set of deliberately flawed, gate-green Tasks — plus one clean control — run through the real pipeline to measure whether the fresh-eyes review catches what the Gate cannot. The runner never judges outcomes and never accepts; comparing findings against planted ground truth is the operator's act. Added in v0.0.3.
_Avoid_: test suite, eval harness, mutation suite

**Arm**:
One member of a battery (flaw or bypass): a Workspace carrying one planted flaw or escape (or none, in the control), its Contract, and the ground truth an outcome is compared against.
_Avoid_: case, scenario, fixture (that names the files)

**Battery outcome**:
The comparison words for one arm against ground truth: hit (CONCERN citing the planted flaw), miss (CLEAR on a flawed arm), noisy hit (CONCERN citing only non-planted nits), false positive (CONCERN on the clean control), failed (technical).
_Avoid_: pass/fail (those are Verdict words)

**Watch battery**:
The instrument that measures the Watch: one planted arm per Watch question (five again since the v0.0.8 re-arm) plus a clean control, run through the real pipeline on the trial daemon with the Watch on, outcomes asserted with the Battery outcome words against pre-registered ground truth (a flag means yes-probability ≥ 0.5 naming the planted evidence). The runner never judges and never accepts; comparison against ground truth is the operator's act at close-out. Added in v0.0.6.
_Avoid_: eval suite, calibration set (that is the later tooling)

### Permissions

**Permit ask**:
The daemon's question whenever an agent wants to run a shell command it cannot run unasked (or, under some modes, edit a file). Since v0.0.4 the plugin answers every ask from a contracted Agent itself; Paseo persists no record of its own, so the ledger's `permit_allowed` / `permit_denied` lines are the audit trail an ask leaves. Under ADR 0045 (Lean Permit Recording), `Supervisor`, `Lead`, and dispatcher seats record only violations (`permit_denied` and `git_blocked`) in `ledger.jsonl` (`deny-only`, never appending routine `permit_allowed` lines for seat read/status/MCP calls), and `Peer` (`Agent`) `permit_allowed` events record lean metadata (`task`, `agent`, `permission`) without full `command` payload strings (full `command` strings are persisted strictly on `permit_denied` and `git_blocked`).
_Avoid_: permission prompt (the daemon's UI word), approval, grant, `Supervisor`/`Lead` `permit_allowed` ledger spam

**Choke policy**:
The Layer-2 runtime judge over permit asks (`agent.permission_asked`) from contracted working Agents and from project seats (`Supervisor`, `Lead`, and registered `dispatchers`, ADR 0015, ADR 0016, ADR 0019, ADR 0044, ADR 0045): for contracted working Agents (recognized strictly by a `Task worktree` path or non-seat Agent binding), it applies default-allow with a small deny-list — the dangerous-git vocabulary on any spelling, direct calls to Paseo's native agent-lifecycle tools (`seat-paseo-tool-fence`), and writes outside the writable set (workspace ∪ /tmp ∪ TMPDIR ∪ factory state dir, excluding `<stateDir>/{projects,ledger.jsonl,correlations.json}`). For `Supervisor`, `Lead`, and dispatcher sessions standing at `<project-root>`, it enforces the `Seat write fence` (`seat-write-fence`) and `seat-paseo-tool-fence`, stripping literal heredoc payloads (`<<EOF ... EOF`, `<<'EOF' ... EOF`, `<<-EOF ... EOF`) on non-interpreter shell commands (`cat`, `tee`, etc.) before `splitShellSegments` and `extractWriteTargets` inspect the command so English prose (`touch`, `install`, `rm`, `git`) and Markdown symbols (`> Note`, `>= 0.5`) inside documentation heredocs never trigger false-positive `seat-write-fence` denials while interpreter heredocs (`python3 - <<'PY'`, `node <<'JS'`, `bash <<'EOF'`) keep their body intact for inspection (ADR 0044), and auto-allowing safe read, bash, and `paseo_factory` MCP tool calls silently (`deny-only` in `ledger.jsonl`, ADR 0045) so seats with `auto_accept: false` or `modeId: "auto"` run unattended without blocking on human permission prompts or bloating the Project's `Ledger`. Strictly on `opencode` sessions (`resolveEffectiveProviderFamily(...) === "opencode"`), when a `Bash` ask's violation is purely a bare Layer-3-shimmed binary (`git`, `npm`, `npx`, `pnpm`, `yarn`, `bun`, `pkill`, `kill`, `killall`, `paseo`, `gh`) whose wrapper exists in `<stateDir>/bin`, Layer 2 delegates the refusal to Layer 3 (`exit 126` + `stderr` + `git_blocked`) so OpenCode v2 never aborts the turn with `Permission.DeclinedError`, while non-OpenCode providers (`pi`, `claude`, `codex`, `copilot`, `omp`, `antigravity`) remain untouched (ADR 0019). A deny is choke-and-record: one ledger line, one report line, no mid-task escalation channel.
_Avoid_: sandbox, warden (that would be daemon-wide), allowlist (the stance is the opposite), parsing non-interpreter heredoc prose as shell commands, recording `permit_allowed` in `ledger.jsonl` for `Supervisor`/`Lead` seats

**Seat write fence**:
The 3-layer mechanical write and tool boundary on `<project-root>` and `<stateDir>` for `Supervisor`, `Lead`, and any normal chat session that has dispatched a directive via `factory supervisor dispatch` (ADR 0015, ADR 0016, ADR 0019, ADR 0044, ADR 0046):
1. **Layer 1 (Provider-Native Harness & `providerOptions` / `modeId` / `featureValues` Lock):** On `agent.create`, `opencode` sets `featureValues: { auto_accept: true }`, `toolPolicy: { preapproved: [] }`, `modeId: "build"`, and `providerOptions: { permission: { edit: "deny", task: "deny", bash: "ask", skill: ... } }`; `claude` sets `providerOptions: { disallowedTools: ["Edit", "Write", "MultiEdit", "NotebookEdit", "Task", "mcp__paseo__create_agent", "mcp__paseo__kill_agent", "mcp__paseo__archive_agent", "mcp__paseo__update_agent"] }` (plus `mcp__paseo__send_agent_prompt`); `codex` sets `modeId: "auto"` and `providerOptions: { features: { multi_agent_v2: false } }`; `pi` sets `defaultTools: ["read", "bash", "grep", "find", "ls"]` in `settings.json`; `zcode` sets `ZCODE_DISALLOWED_TOOLS: "Write,Edit,MultiEdit,NotebookEdit,DeleteFile"`, `ZCODE_DYNAMIC_WORKFLOW_MODE: "disabled"`, `ZCODE_ACP_MODE: "guarded"`, `featureValues: { auto_accept: false }`, and `modeId: "guarded"` (ADR 0046); `copilot` sets `featureValues: { auto_accept: false }` and `modeId: "...#plan"` / `"...#agent"`; `omp` sets `modeId: "write"`; and `antigravity` auto-provisions `~/.gemini/config/plugins/paseo-factory/hooks.json` with a `PreToolUse` hook that denies disallowed edits and commands when `PASEO_FACTORY_SEAT` is set (sharing `stripNonInterpreterHeredocs` with Layer 2, ADR 0044).
2. **Layer 2 (`Choke policy` on `agent.permission_asked`):** Refuses (`seat-write-fence`) any file-write tool or shell command targeting paths in `<project-root>` outside the project memory and planning whitelist (`AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, `GLOSSARY.md`, `.gitignore`, `.worktreeinclude`, `docs/**`, `.scratch/**`) or mutating `<stateDir>/{projects,ledger.jsonl,correlations.json}` directly (after stripping non-interpreter heredoc bodies via `stripNonInterpreterHeredocs`, ADR 0044), and refuses (`seat-paseo-tool-fence`) direct calls to Paseo's native agent-management tools (delegating bare Layer-3-shimmed `Bash` commands to Layer 3 strictly on `opencode` sessions so OpenCode v2 returns `stderr` without aborting the turn, ADR 0019).
3. **Layer 3 (OS `PATH` Shims in `<stateDir>/bin`):** Enforced by the `Git shim` (`supervisor-git-fence` / `lead-git-fence`), package-manager shims (`npm`, `npx`, `pnpm`, `yarn`, `bun`), and process-protection shims (`pkill`, `kill`, `killall`, `paseo`, `gh`) (ADR 0016, ADR 0019, ADR 0044).
_Avoid_: prompt-only rule, advisory boundary

**Git shim**:
A `git` wrapper in the hook-injected PATH dir (`<stateDir>/bin`, alongside package-manager shims for `npm`, `npx`, `pnpm`, `yarn`, `bun` and process-protection shims for `pkill`, `kill`, `killall`, `paseo`, and `gh`, backed by self-contained scripts staged in `<stateDir>/runtime-bin/` and `<stateDir>/shared/` plus newest-managed-checkout resolution across Paseo `updateSource` so `<stateDir>/bin/*` wrappers survive deletion of outgoing `<paseoHome>/plugins/paseo-factory/<uuid>` checkouts, ADR 0016, ADR 0019) that refuses the destructive git subcommands (force/delete push, `reset --hard`, deleting `clean`, working-tree discard on `<project-root>`, `branch -D`, recovery destruction) at exec time no matter who runs them — while permitting working-tree discard (`git restore <file>`, `git checkout -- <file>`) inside isolated `Task worktree`s (`<projectStateDir>/worktrees/<task>`) so Peers can clean up failed experiments before claiming (ADR 0028), permitting `kill` / `pkill` / `killall` signals targeting test or dev-server child processes scoped inside a `Task worktree` (`/projects/<slug>/worktrees/<task>/`, such as `@embedded-postgres` or Playwright/Chromium) when not matching Paseo or factory infrastructure binaries (ADR 0044), and permitting `npx` invocations that launch read-only MCP stdio server packages (`@z_ai/mcp-server`, `@upstash/context7-mcp`, `chrome-devtools-mcp`, `@notionhq/notion-mcp-server`, `@modelcontextprotocol/server-*`, and `*-mcp*` / `mcp-*` server packages) so harnesses booting global user MCP servers do not trigger false `seat-write-fence` blocks at startup (ADR 0031) — plus, under the `Seat write fence` (ADR 0015, ADR 0016, ADR 0019, ADR 0028), blocks `git commit`, `git merge`, `git cherry-pick`, `git rebase`, `git reset`, `git clean`, `git stash`, and branch creation by `Supervisor` on `<project-root>` (`supervisor-git-fence`), blocks `Lead` from committing non-whitelisted source files on `<project-root>` (`lead-git-fence`), and blocks `Agent` (`Peer`) from committing edits to root memory files (`AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`) unless `Contract.scope` explicitly lists them (`memory-write-fenced`) — explanatory stderr line plus one `git_blocked` ledger line (bound to `task: contract.task` strictly when `cwd` is a contracted `Task worktree` and `rule` is not a seat fence rule, ADR 0031); everything else passes through to the real git. Composes with Layer 1 and the Choke policy: the shim nets PATH-resolved git, package-mutating seat commands (`npm`/`npx`/`pnpm`/`yarn`/`bun`), and daemon-killing commands (`pkill`/`kill`/`killall`/`paseo`), the policy nets everything that asks.
_Avoid_: git wrapper (too generic), git hook (different mechanism)

**Bypass battery**:
The instrument that measures the choke: four planted escape arms plus a clean control, run against the real plugin on the trial daemon, outcomes asserted against rules fixed before any run (choked = not executed + exactly one ledger line; escaped; clean; failed). The runner never judges and never accepts, and refuses the prod home.
_Avoid_: pentest, red team, security audit

### Records

**Ledger**:
The append-only per-Project record of every event in a Project (`<stateDir>/projects/<project-slug>/ledger.jsonl`, ADR 0010, ADR 0045); ordinary operation never edits or removes recorded facts.
_Avoid_: log, history, sổ (outside research notes), shared root `ledger.jsonl` mixing multiple Projects

**Ledger event identity**:
The stable identity of one recorded factory fact, preserved when its history is copied or synchronized between machines.
_Avoid_: sequence number, timestamp

**Ledger sequence**:
An event's assigned position in one local Ledger. That assignment retains its meaning when more history is imported.
_Avoid_: event identity, global order

**Ledger import**:
Admission of incoming factory history into a local Ledger after its identity, evidence and local state bindings have been validated. A fetched snapshot can wait for admission while active work continues.
_Avoid_: download, hydration

**Ledger import conflict**:
Incoming history whose relationship to local history, evidence or local state cannot be resolved unambiguously. Its original snapshot is retained for the Owner's resolution.
_Avoid_: newest-wins, merge success

**Report**:
The human-readable account of one Attempt, generated from the Ledger, with every line traceable to a Ledger event.
_Avoid_: summary, biên bản (outside research notes)

**Meter**:
The plugin-owned recorder of token and cost usage across every provider harness (`pi`, `codex`, `opencode`, `antigravity`, `claude`, `copilot`, `zcode`) and every Project seat (`Supervisor`, `Lead`, working `Agent` / `Peer` / `Scrum role`, and headless `Watch` / `Retro` passes) (ADR 0004, ADR 0043, ADR 0046). Rather than relying solely on the Driver or Paseo's volatile, single-turn in-memory `lastUsage`, the plugin extracts authoritative cumulative usage from each provider's native session store through a stat-gated incremental/tail reader (`O(delta)` via byte-offset cursors on append-only JSONL for `pi`/`claude`/`copilot`, 64 KB tail reads of `total_token_usage` on `codex` rollout JSONL, indexed row reads on `opencode` `session_v2`, incremental `idx > lastStepIdx` Protobuf decoding on `antigravity` `steps`, and `sequence > lastStepIdx` SQLite `message` row reads with `~/.zcode/v2/acp-lazy-sessions.json` `acpSid -> zcodeSid` resolution on `zcode` `db.sqlite`, ADR 0046), normalizing all providers into four disjoint additive token buckets (`inputUncachedTokens + cacheReadTokens + cacheWriteTokens + outputTokens = totalTokens`, with `reasoningTokens` reported as a subset of `outputTokens`) plus `totalCostUsd` when metered. Persists across two complementary tiers without bloating the Ledger: (1) exactly one task-scoped `meter_written` line appended to `ledger.jsonl` at each Task Attempt's / Peer's terminal boundary, and (2) an idempotent per-Project rollup (`<projectStateDir>/usage.json`) keyed by `agentId` (retaining `seat`, `task`, `attempt`, `provider`, `harness`, `model`, `turns`, token buckets, timestamps, and `nativeSessionRef` for per-turn auditability) updated debounced on `agent.turn_ended`, finalized on seat rotation/retirement, and lazily backfilled once from `<paseoHome>/agents/` for historical Projects. A recorder, never a judge: no token budgets, no automatic spending cutoffs, and Verdicts remain unchanged. Added in v0.0.8; upgraded to plugin-owned multi-provider two-tier metering in ADR 0043; extended with `zcode` SQLite metering in ADR 0046.
_Avoid_: cost tracker, billing, accounting, per-turn `ledger.jsonl` spam, double-counting cached or reasoning tokens

### Running

**Spawn**:
Starting a contracted Task's Agent: a `spawn` request through the spool, validated by the plugin (request shape, caller seat authority — refused if called by `Supervisor` or a working `Agent`, task known and not accepted, no workspace conflict, and no currently running/initializing `Peer` already bound to that Task — `peer-already-running`, while any stopped `idle` or `error` `Peer` from a prior run on that Task is automatically canceled and archived before replacement so at most one active `Peer` ever operates in a `Task worktree` at a time, ADR 0031), automatically allocating or reusing the Task's isolated `Task worktree` (`<projectStateDir>/worktrees/<task>` on branch `factory/<task>`) server-side whenever `request.worktree` is omitted on a root-workspace `Contract` so a `Peer` never falls back onto `<project-root>` or shares the `Lead`'s Paseo `workspaceId` (where archiving an outgoing `Lead` during `Lead handoff` would trigger Paseo's `cascadeArchiveChildren` against a same-workspace child), and recorded as exactly one ledger line — `spawn_dispatched` (always carrying the resolved `worktree` path) or `spawn_refused` with its rule — before any agent exists, with the Task's Paseo workspace bound to the Project's `projectId` and the working Agent created with `parent: leadAgentId` (ADR 0015, ADR 0028, ADR 0031, ADR 0045). Added in v0.0.5; workspace-bound and parented in ADR 0015; freed from pre-declared scope mandates in ADR 0028; guarded by the Single-Active-Peer Law in ADR 0031.
_Avoid_: launch, fork, dispatch (that names the happy ledger line), spawning a `Peer` directly in `<project-root>` when `request.worktree` is omitted

**Driver**:
`factory run <task>… [--provider <p[/m]>]` — the command that takes explicit task ids, creates each task's branch, spawns each Agent (through the spool, falling back to the `worker` lane in the Lane config when `--provider` is omitted, ADR 0009) and watches to verdict, printing each task's verdict at its own terminal moment and exiting 0 only when every task ran green with zero refusals. It never sets Contracts and never Accepts; it stops at verdicts. Since v0.0.10 its watch loop carries the Lead's stall predicate as a rider (the announced path to a standing plugin loop); since v0.0.12 (ADR 0008) it stays watching across red Attempts below the Attempt ceiling and executes at most one automatic Respawn on Substrate death. Carrying a seat's act does not make it one. Added in v0.0.5.
_Avoid_: orchestrator, runner, supervisor, lead (those are seats, ADR 0006 — the Driver is neither)

**Attempt ceiling**:
The hard cap of three Attempts per Task (`MAX_ATTEMPTS = 3`, fixed in code, never configuration). Enforced plugin-side at `Claim` (a fourth Claim is refused before any Gate starts) and at `Spawn` / `Respawn` (`spawn:attempt-ceiling` / `respawn:attempt-ceiling`), and observed by the Lead rider: when Attempt 3 finishes red, the Task ends immediately in `needs_human` (`reason: "attempt-ceiling"`). Added in v0.0.12 (ADR 0008).
_Avoid_: retry limit, max retries, attempt budget

**Respawn**:
Replacing a contracted Task's Agent after `Substrate death`: a `respawn` request through the spool naming the dead Agent (`died_agent`), validated by the plugin (at most one automatic Respawn per progress marker — the latest `spawn_dispatched` or `gate_finished`) and recorded as `respawn_dispatched` or `respawn_refused` before the replacement Agent is created on the Task's branch with uncommitted working-tree fragments cleaned to `HEAD`. A second `Substrate death` with no new Attempt between them ends in `needs_human` (`reason: "died-after-respawn"`). Added in v0.0.12 (ADR 0008).
_Avoid_: restart (implies reviving the same daemon session), retry (an Attempt word), re-spawn

**Denial-stall**:
A Task whose Agent's turn ended at a denied permit ask: the last thing the Ledger shows for the Task is a denial, no Claim after it, and a fixed grace has elapsed. The Lead's only trigger. Distinct from spawn-then-silence, where nothing at all follows the spawn — substrate death, not a chokee's stall.
_Avoid_: stuck (too broad), blocked, hung

**Substrate death**:
The death of a spawned Agent's machinery — the agent no longer exists on the daemon (its timeline answers "not found"), or exists but shows no Life signal for the no-growth bound. What a Denial-stall is not: a stall is a live chokee; a substrate death has no chokee to poke. Classified by the driver's two doors, both read from the daemon timeline (ADR 0007).
_Avoid_: crash, hang (a live stall's words), zombie, false death (the retired incident class — a history word, not a state)

**Life signal**:
The observable evidence that a spawned Agent is alive and working: its daemon timeline entries growing. What the watch reads to tell working silence from Substrate death on lanes whose silence is honest — ask-less lanes write nothing to the Ledger between Spawn and Claim. Added in v0.0.11 (ADR 0007).
_Avoid_: heartbeat (implies the agent transmits it; the daemon is read, not pinged), liveness probe, ping

**Re-poke**:
The Lead's one act: a fixed-text message to a stalled Agent — continue by a route that needs no denied permission and make your Claim, or end the turn stating what you need from the Owner. Exactly one per Task, enforced where requests land, not hoped for; never sent into a running turn or over a pending ask.
_Avoid_: nudge, retry, wake (richer machinery's word), reminder

**Needs-human**:
The Ledger event (`needs_human`) the Lead writes when bounded automation is exhausted — when a Re-poke is spent and the Denial-stall persists (`denied-again`, `silent-after-repoke`), when a Task hits the Attempt ceiling (`attempt-ceiling`), or when a Task suffers Substrate death again after its one automatic Respawn (`died-after-respawn`) — each corroborated by its own Ledger evidence seqs. The Supervisor relays it to the Owner in words at its next turn, at leisure (only Acceptance closes a Task).
_Avoid_: alert, escalation ticket, incident (a different kind, its own later writer)

**Parallel run**:
The Driver running more than one contracted Task at once: the number of task ids on the invocation is the ceiling, and every Task works in its own isolated `Task worktree` (`<projectStateDir>/worktrees/<task>`, ADR 0010, ADR 0028). Added in v0.0.5; updated in ADR 0028.
_Avoid_: concurrency (too broad), batch, pool

**Unattended loop**:
A driver loop that takes approved Contracts, spawns Agents, runs Gates and records Verdicts without the Owner present. It commits to branches only; landing to main is always a human act. The Driver is its first shipped slice (v0.0.5); schedules and no-Owner operation remain later rows.
_Avoid_: autopilot, background job, cron

**Lead mailbox**:
The per-Project append-only bidirectional seat mail ledger (`<projectStateDir>/mailbox.jsonl`, ADR 0013, ADR 0015, ADR 0031) written exclusively by the single-writer plugin on a serialized per-Project lane, fed by atomic spool requests (`factory supervisor dispatch`, `factory lead dispatch`, and `factory supervisor report` via `<stateDir>/spool/requests/<id>.json`, ADR 0004, ADR 0015), UI quick dispatch, and Agent terminal outcomes (`Verdict` completed, `Needs-human`, with `notifyPeer` checking `driverWaveInFlight` strictly against the owning Project's `Ledger` slice so concurrent Projects never block each other's `Verdict` delivery). Records four immutable event types (`mail_queued`, `mail_delivered`, `mail_acked`, `mail_requeued`) partitioned by recipient seat (`to: "lead" | "supervisor"`, defaulting to `"lead"`): queued items wait while the recipient seat (`Lead` or `Supervisor`) is `running`, `initializing`, waiting on a permission ask (`attentionReason === "permission"`), or during a Lead handoff (`rotation_pending` or `handing_over`), lazily auto-ensure and self-heal the recipient seat when absent or in `status === "error"` on the next mailbox pump (preserving any in-flight `pendingHandoff` and first-turn `Seat kickoff packet` until `outcome === "completed"`, without looping into an active network outage when no `mail_requeued` batch is being retried), batch-deliver into a single turn when the recipient seat is ready (`status === "idle"` or Paseo idle-collected `status === "closed"` with `archivedAt === null`, waking a sleeping `"closed"` seat automatically on `.send(prompt)` and re-pumping when an interactive seat session resumes on `agent.open.before` / `agent.session_open`), acknowledge only when that turn ends with `outcome === "completed"`, and automatically requeue (with at most one automatic re-pump per `mailId` after seat self-healing) if the turn fails or is interrupted.
_Avoid_: mutable JSON outbox (`outbox.json`), SQLite queue, direct `agents.send` bypass, Paseo `agents.resumeOnStartup` injecting `"Resume working."` prompts ahead of `startupRecovery()`

**Supervisor mailbox**:
The `to: "supervisor"` recipient slice of a Project's `mailbox.jsonl` (ADR 0015, ADR 0031): fed by Owner `/factory` directives (`factory supervisor dispatch`), Lead completion/escalation reports (`factory supervisor report`), and automatic `Needs-human` peer notifications. Like the Lead slice, it auto-ensures and self-heals the Project's `Supervisor` seat on demand, holds queued items while `Supervisor` is `running`, `initializing`, or waiting on a permission ask (`attentionReason === "permission"`), batch-delivers (`# Supervisor mailbox — <N> item(s)`) when `Supervisor` is ready (`status === "idle"` or Paseo idle-collected `status === "closed"` with `archivedAt === null`), and settles with `mail_acked` or `mail_requeued` (with a bounded 1-shot retry pump) on `agent.turn_ended`.
_Avoid_: separate `supervisor-mailbox.jsonl` file, direct `agents.send` bypass

**Pause (user)**:
The Owner's intentional suspension of a seat — pausing an agent mid-turn, stopping a turn, or sleeping/powering down the machine. Invisible to the Paseo protocol (`AgentStatus` has no `paused`; a pause surfaces only as a canceled turn or as a live non-`error` agent sitting `idle`/`closed`), so the machine honors it by inference, never by a persisted frozen state (ADR 0050): a paused-but-alive `Peer` on an open spawn round counts as in flight and holds `rotation_pending` across restarts, a paused outgoing `Lead` gets its handoff extraction held and re-sent rather than fused over, and the machine never treats `Pause (user)` as a completed `Peer` outcome. Distinguished from `idle` (a daemon status the machine reads) and from in-flight (the machine's durable judgment from the `Ledger` plus the live snapshot).

**Lead handoff**:
The deterministic runtime succession of a Project's Lead when its context window usage reaches the fixed `128,000` token mark (`128k`, read from Paseo's `lastUsage.contextWindowUsedTokens` with the multi-provider `Meter` incremental native-session fallback across `pi`, `codex`, `opencode`, `antigravity`, `claude`, and `copilot`, ADR 0013, ADR 0018, ADR 0027, ADR 0031, ADR 0043, ADR 0044). Crossing `128k` mid-turn or at the turn boundary (`agent.turn_ended`) marks `rotation_pending` without interrupting the active turn and holds the `Lead mailbox` (`mail_queued`). If an unaccepted Task's `Peer` still has unsettled `Peer` work in flight (`projectPeerInFlight` — checking live `running`/`initializing` `Peer`s across `driverWaveInFlight` and `boundTaskPeers`, plus any `idle` `Peer` whose latest turn ended with `outcome !== "completed"` on an unsettled `Task` so a mid-turn network drop or `EPIPE` on the `Peer` never triggers a premature `Lead handoff`, and — durably, across daemon restarts and plugin updates (ADR 0050) — any live non-`error` `Peer` (`idle`/`closed` included) on an open spawn round over an unsettled `Task` with no terminal event, so a `Pause (user)` of the `Peer` never becomes a quiet point, while excluding any `Task` whose folded `Ledger` status in the current `Contract epoch` is already `Peer`-terminal — `ready-to-accept` / `GREEN`, `needs-human`, `red` at `MAX_ATTEMPTS = 3`, or a queued `from: "peer", kind: "needs_human"` blocker in `mailbox.jsonl` — so `notifyPeer` / `dispatchLead` never self-blocks on the calling `Peer`'s still-`running` turn), the runtime holds the Project in `rotation_pending` (keeping the outgoing `Lead` live and visible in Paseo while queuing incoming `Supervisor`, `Owner`, and `Peer` mail in `mailbox.jsonl`) until the `Peer` wave settles (`notifyPeer`, `dispatchLead`, `observePeers` on `Peer` `agent.turn_ended` / `sweepPeers`, or `pumpAll` observing `projectPeerInFlight === false`). Once no `Peer` is in flight, the plugin transitions `rotation_pending` → `handing_over` (`beginHandoff`) and steers one bounded **reply-first** handoff-extraction turn (`renderHandoffExtractionPrompt`, instructing the outgoing Lead to output the entire Markdown handoff directly in its final assistant message without running shell commands or writing files outside `<project-root>`, ADR 0044) guarded by a dual-fuse safeguard (the runtime trips the fuse only when the outgoing `Lead` is absent/errored, the extraction send fails, or the elapsed `180s` timeout (`HANDOFF_EXTRACTION_TIMEOUT_MS = 180_000`) finds the Lead still `running`; an alive `idle`/`closed` Lead gets the extraction prompt re-sent instead — at most 3 sends per `handing_over` episode — and every completion that did not come from a `completed` extraction turn appends one `needs_human` mail to `Supervisor` (ADR 0050 amending ADR 0018's silent completion)). When the extraction turn completes (`onLeadTurnEnded`), the plugin extracts the outgoing Lead's assistant handoff text from `input.timeline` or by refetching the tail timeline (`daemon.agents.ref(leadId).timeline.refetch({ direction: "tail", limit: 20 })` when `timeline: []` on Paseo `0.13.0+`, ADR 0027, ADR 0044), caps UTF-8 bytes cleanly at `8 KB` (`LEAD_HANDOFF_MAX_BYTES` via `capHandoffText`, never failing the handoff when the model writes past the cap; the extraction prompt forbids copy-pasting active `Contract.description` blocks verbatim or writing detailed post-mortems of already-accepted waves, ADR 0044, ADR 0047), and persists `<projectStateDir>/lead-handoff.md` in Node.js (`writeFileSync`, accepting a freshly written disk file only as a secondary fallback when non-empty and not an error/refusal note, and **preserving any existing last-known-good `lead-handoff.md` on disk** with a 1-line staleness notice in `renderSuccessorKickoff` whenever extraction times out, exhausts its re-send cap, or produces an empty/refusal reply — an interrupted/canceled extraction turn instead holds `handing_over` and re-sends (ADR 0050 amending ADR 0044), ADR 0044). Upon extraction completion or fuse trip, the plugin finalizes the outgoing Lead's cumulative token snapshot in `<projectStateDir>/usage.json`, archives the outgoing Lead, silently creates a fresh successor Lead (`0%` context), resets `rotationState = "normal"`, and immediately delivers the unified Turn-1 kickoff combining the `Seat kickoff packet`, the machine-verified Active Peer Roster (full status/agent/worktree/attempt/report rows strictly for unaccepted Tasks, with already-accepted Tasks summarized into one compact line, ADR 0047; resolved across the `Ledger`, `CorrelationRegistry`, and live daemon worktrees, preferring `running`/`initializing` or the newest live `Peer` in the current `Contract epoch` rather than older `idle` `Peer`s at the tail of `daemon.agents.list`, ADR 0031), the `Ledger` state digest, `lead-handoff.md`, and all held `Lead mailbox` items (including the `Peer`'s completed `Verdict` or escalation mail, retaining `pendingHandoff` across failed Turn-1 deliveries and reconstructing `pendingHandoff` from `<projectStateDir>/lead-handoff.md` when replacing an errored or restarted successor `Lead` that had not yet completed Turn 1, ADR 0031).
_Avoid_: fourth monitor agent role, mid-turn kill, context compaction on Lead, multi-turn handoff prompt storm, ordering outgoing Lead to shell-write outside `<project-root>`, clobbering last-known-good `lead-handoff.md` on extraction timeout, archiving the outgoing Lead and spawning a blank 0-message successor Lead while a `Peer` is still running, waiting for a `Peer` process turn to become `idle` after its `Task` has already reached a `GREEN` `Verdict` or `Needs-human` in the `Ledger`

**Peer handoff**:
The deterministic runtime succession of a working `Agent` (`Peer`) inside its `Task worktree` when its context window usage reaches the fixed `160,000` token mark (`160k`, read from Paseo's `lastUsage.contextWindowUsedTokens` with the multi-provider `Meter` incremental native-session fallback across all 6 harnesses, ADR 0034, ADR 0043, ADR 0044) before the Task's `Claim` settles. Crossing `160k` triggers a bounded **reply-first** handoff-extraction turn on the outgoing `Peer` (`buildPeerHandoffExtractionPrompt`, instructing the outgoing `Peer` to output the entire Markdown handoff directly in its final assistant message without running shell commands or writing files to disk, guarded by a `180s` fuse safeguard, where the plugin server extracts the assistant reply from the turn timeline or tail refetch, caps UTF-8 bytes cleanly at `12 KB`, and writes `<projectStateDir>/peer-handoff-<task>.md` in Node.js while accepting a freshly written `<worktree>/.paseo-peer-handoff.md` or `<projectStateDir>/peer-handoff-<task>.md` file as a secondary fallback, ADR 0044), finalizes the outgoing `Peer`'s cumulative token snapshot in `<projectStateDir>/usage.json`, archives the outgoing `Peer`, and — up to at most **one** automatic `Peer handoff` per `Contract epoch` (`maxPeerHandoffs = 1`, i.e., at most two `Peer` sessions per epoch) — spawns a fresh successor `Peer` (`0%` context) in the same `Task worktree` with the original `Contract` brief plus the outgoing `Peer`'s handoff digest and current worktree git state. If the successor `Peer` also crosses `160k` in the same `Contract epoch` without a green `Claim`, the runtime archives the `Peer` and escalates a structured `BLOCKED (context-ceiling)` notification to `Lead` with the current worktree commit/diff summary so `Lead` can inspect and split the remaining scope into a follow-up wave rather than spinning additional `Peer`s indefinitely (ADR 0034).
_Avoid_: unbounded 300k+ Peer sessions, infinite Peer rotation loops, discarding uncommitted worktree progress on rotation, ordering outgoing Peer to shell-write outside `<worktree>`
